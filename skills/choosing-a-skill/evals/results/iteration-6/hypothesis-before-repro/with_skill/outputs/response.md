Yes. I'll run `diagnosing-bugs` on this, and the first phase is the whole job right now: build a **tight loop** that goes **red** on this specific bug. Nothing else starts until I have one.

That matters more than usual here because one-in-five is a *rate*, not a clue. It doesn't tell us the mechanism — and it means any fix I make has roughly an 80% chance of looking like it worked on the very next load. So the loop has to be able to distinguish "fixed" from "got lucky", which means driving the failure rate up until it's reliable enough to debug against, not catching one failure and reasoning from that single capture. A loop that goes red half the time is workable; one that goes red 1% of the time isn't.

Concretely, Phase 1 looks like: get the page loading under a command I can run repeatedly and unattended, capture the error with a stack trace rather than just the message, and then push the rate up — repeat the load N times and count, and stress whatever the loop shows is varying between a passing load and a failing one until failures dominate. The completion criterion is one command I've already run at least once that is red-capable, deterministic, fast, and runnable by an agent.

I'm deliberately not naming a cause yet. `cannot read property 'id' of undefined` on an intermittent page load has several plausible mechanisms, and if I pick a favourite now the loop stops being a way to find the cause and becomes a way to confirm my guess — every observation after that gets read through it. Instead I'll treat the candidates as things the loop has to be able to *force*: it should be able to make the failing load happen on demand, whatever the varying input turns out to be (timing, request ordering, cached vs cold state, a particular account or session shape, a specific entry route to the page). If the loop can force it, the cause falls out of the next phase; if it can't, that tells me something too.

One honest caveat up front: this depends on my being able to actually drive the page — load it repeatedly, vary the conditions, and read the error. If it turns out I can't reach a working environment, I'll tell you that and stop rather than switch to reading the code and reasoning about what the ordering *probably* is. Guessing from source is exactly the failure this phase exists to prevent, and it doesn't get better for being the only option left.

Where this goes next depends entirely on what the loop shows — I'd rather report back with a red command in hand than commit to steps three and four now.
