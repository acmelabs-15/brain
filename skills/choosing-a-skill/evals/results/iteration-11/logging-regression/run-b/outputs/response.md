Before I add any logging, I want to flag a fork in what you asked for, because it changes which skill I run.

"Add proper logging to the checkout flow" is a real, standalone job — `observability-and-instrumentation` covers exactly that, and its description even lists "production issues are reported but you can't tell what happened" as a trigger. So this is a genuine collision, not one I'm dismissing. But that skill is a checklist you consult once you know what you're looking for, not a workflow you run at a symptom. Run it here and what I produce is a list of the places one usually logs in a checkout — hypothesis-first reasoning wearing a checklist for cover. If the failure is somewhere I didn't guess, the new logs come back clean and we've spent a deploy cycle to learn nothing.

The other read is that "keeps failing for some users, no idea why" is a bug with an unknown mechanism, which routes to `diagnosing-bugs`. That skill's first phase is the whole point of it: build a **tight loop** — one command I've actually run that goes **red** on this specific failure. And "some users" is a rate, not a cause. A one-in-N failure is a number to drive toward certainty before I reason from it; if I catch one failure and theorise from that single capture, a fix that looks right has most of a chance of appearing to work regardless.

So here is what I commit to: I'm starting with `diagnosing-bugs`, and the instrumentation is how I build the loop rather than the deliverable. Concretely, the first pass is the narrowest thing that turns "some users fail" into a signal I can watch — a correlation/request id threaded through the checkout path, and logging at the boundaries where the flow can leave: each external call (payment, tax, inventory, auth) with its outcome and latency, each validation or branch that can reject, and every catch that currently swallows. Boundaries first because they cost little and they tell me which segment to open up next.

I need two things from you to make that loop real, and they're the difference between a diagnosis and a guess:

- **Where can I watch the output?** A log aggregator I can query, a staging environment I can drive, a way to replay a failed session — anything. If checkout only fails in production and I have no way to observe or reproduce it, I'll say so and stop rather than fall back on reading the code and reasoning about what probably happens. That fallback is precisely what this phase exists to prevent.
- **What's the failure rate and its shape?** Rough numbers are fine. If it's ~1%, my first target is driving that rate up — same payment method, same cart shape, same region, same time of day — until failures are frequent enough to debug against. `diagnosing-bugs` treats a 50% flake as workable and 1% as not.

I'm deliberately not opening with a ranked list of likely causes (timeout, race, third-party flake). Naming a favourite now turns the instrumentation into something that confirms a theory instead of finding one, and I'd read every later log line through it. The things I want the loop to force are simply: which stage the flow dies in, whether the failing users share an attribute, and whether the failure is inside our code or at an external boundary.

Once the loop goes red on demand, I'll come back to `observability-and-instrumentation` for the permanent instrumentation — the structured fields, levels, sampling, retention, and PII handling that checkout logging needs when it stays in the codebase. That's the right moment for the checklist, because by then I'll know what's worth recording. The next steps after the loop depend entirely on what it shows.

One caveat worth naming now: checkout logs touch payment and personal data. Whatever goes in, card numbers, CVVs, and full PII stay out — I'll log identifiers and outcomes, not payloads.
