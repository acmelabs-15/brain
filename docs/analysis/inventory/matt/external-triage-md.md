## Design intent — required
Serves as the public documentation, discoverability page, and reference guide for the `/triage` skill on Matt Pocock's AI Hero platform (`aihero.dev/skills-triage`). It addresses the challenge of handling inbound, unvetted work arriving from external sources (raw bug reports from users, community feature requests, external pull requests) into a project's issue tracker. Unlike internally originated work that flows through the main design chain (`grill-with-docs` → `to-spec` → `to-tickets` → `implement` → `code-review`), inbound work arrives in whatever unvetted shape the reporter left it. `triage` acts as an on-ramp and gatekeeper: it normalizes issues through a two-dimensional role model (one category role: `bug` or `enhancement`; one state role: `needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`), verifies claims against the codebase (reproducing bugs, running PR test suites, checking redundancy against existing features, and checking prior rejections in `.out-of-scope/`) before writing briefs, operates in an advisory "recommends and waits" mode rather than unilaterally altering tracker state, and produces durable agent briefs naming types and behavioral contracts without brittle file paths or line numbers. Without this page and skill, open-source maintainers and development teams would have no structured funnel for external requests, risking agents picking up unverified bugs, polluting trackers with invalid labels, or bypassing triage discipline.

## Observations
- On-ramp positioning: Positioned as an on-ramp for external, inbound work rather than a sequential stage in the main authoring chain ("not a step in the main chain." — external/triage.md:73). Internally originated tickets produced by `to-tickets` already carry `ready-for-agent` by construction, so running `triage` on them is wasted work.
- Durable agent briefs: Explicitly specifies that agent briefs must be durable rather than precise ("rather than precise, because an issue can sit in" — external/triage.md:44; "ready-for-agent" — external/triage.md:44; "for weeks while the code moves underneath it." — external/triage.md:44), mandating types, signatures, and behavioral contracts while prohibiting file paths and line numbers ("name types, signatures and behavioural contracts, and never file paths or line numbers." — external/triage.md:44).
- Out-of-scope knowledge base: Rejected enhancements are recorded into `.out-of-scope/` as short design documents matched by domain concept rather than keyword ("matches by concept rather than keyword, so &quot;night theme&quot; matches" — external/triage.md:40; "dark-mode.md" — external/triage.md:40), whereas already-implemented features are deliberately omitted to avoid poisoning deduplication checks ("Nothing is written to <code class=\"ah-code-inline\">.out-of-scope/</code>, because it&#x27;s a built feature, not a rejected one, and filing it there would poison the dedup checks." — external/triage.md:39).
- Two-dimensional role invariant: Enforces a strict data model where every triaged item carries exactly one category role (`bug` or `enhancement`) and exactly one state role (`needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`).
