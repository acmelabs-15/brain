## Position after review

**Teamwork fits this project.** A long project, deep research, a human gate, then a build with tests is the documented use case ("large software projects, complex simulations, and deep research tasks… When work spans multiple days"). The roles map onto METHOD's phases: Explorers for read-only research, Workers for writing, Critic and Auditor for independent verification against a rubric, Orchestrator succession against context degradation. The researcher's "misusing" verdict in Part A below was too broad and is corrected here: the mechanism is right.

**What is wrong is granularity and the interview.** Today one Teamwork team runs per work unit, five at once, and the primary agent answers the Phase 1 scoping interview itself. That multiplies the eight-role stack by five and leaves "Independent Verification" — the one documented lever that produces rubric-judged markdown — filled in by the agent rather than by you. The fix: **one Teamwork run per phase (or per batch of units), with Peter answering the Phase 1 interview.** In it: Independent Verification = R1–R11 plus `coverage.ts` and `quote-check.ts`; Acceptance Criteria = the phase's done criteria from METHOD; Project Working Directory = the repo, not `~/teamwork_projects`; integrity mode `development`. Inside that run the Orchestrator does the fan-out over units, and Critic/Auditor judge against the rubric — which is what those roles are for.

**Integrity mode.** `development` is correct. `demo` and `benchmark` govern code provenance (copying OSS logic, external tools, reading tests, stdlib-only) and do nothing for extraction fidelity; `benchmark` could even forbid the parsing tools. The fidelity lever is the Phase 1 rubric, not the mode.

**Boost.** Not for Phases 3–6. Boost is immediate execution with no scoping, a three-tier hierarchy whose workers implement, and a verification loop that "validates the combined solution against full test suites and edge cases." Every documented use case is code. Phase 4's difficulty is judgment across conflicting sources; there is no test a decision can fail, so Boost's loop has nothing to verify. Teamwork's **Document Review** path ("review this… / critique this…" — "multi-angle critique and synthesis of papers, RFCs, and design docs") is the documented fit for Phase 4V and Phase 5 review. Boost belongs in **Phase 7**, invoked inside the Teamwork run for a build unit that turns out to be a hard, test-verifiable problem.

**Structured state.** Part B lists exactly what is machine-readable. The statusline `subagents[]` array is undocumented; the only documented per-subagent feed is headless `stream-json` `subagent_info`.

Part C's decision rule and Part E item 1 below are the researcher's original text and are superseded by this section where they differ.

## A. TEAMWORK FEATURE AUDIT

### A1. What Teamwork is for (scope statement) [D]
TW: "runs a collaborative multi-agent team designed for large software projects, complex simulations, and deep research tasks. When work spans multiple days, involves refactoring across dozens of files, or tackles open-ended math and systems challenges…" Four listed problem classes: large-scale refactoring/migrations; systems research & simulation; mathematical proofs & research; "Long-running projects without context bloat". B‑TW: "built for problems that are too large, too uncertain, or too open-ended for a single agent loop."
**User's usage:** *Misusing.* Per-work-unit mechanical extraction into markdown is none of the four classes. The docs' own recommendation for sweeps is plain subagent fan-out: "For large-scale sweeps or multi-file refactoring, direct the primary agent to spawn concurrent background subagents" (https://antigravity.google/docs/cli/best-practices).

### A2. Phase 1 — scoping interview & prompt artifact [D]
TW: "the main Antigravity agent conducts a structured interview with you. The interview follows a simple principle: **Specify What, Not How**". Five fields:
1. **Scope & Objectives** — "what you want built, its purpose (demo, production, eval, exploration), and the audience."
2. **Requirements** — "several requirement blocks covering only what you actually care about."
3. **Independent Verification** — "an objective check for each requirement — a test suite, reference benchmark or metric script, or an independent agent judging against an explicit rubric."
4. **Acceptance Criteria** — "clear, testable criteria for considering the project complete."
5. **Project Working Directory** — "defaulting to `~/teamwork_projects/{PROJECT_NAME}`."
Plus, the integrity mode: "your agent asks which shortcuts should be off-limits and maps your answers to a mode, which is recorded in the prompt artifact."
Output: "a reviewable **prompt artifact**. You can review the prompt, adjust details, and approve execution with a single confirmation." SC calls it "a binding specification plan"; the architecture SVG labels it "🔒 Specification Plan — Ground-truth specification" (https://antigravity.google/assets/image/blog/teamwork-multi-agent-architecture.svg).
[C] Medium (Subrahmanyam, Aug 27 2026, https://medium.com/google-cloud/antigravity-teamwork-for-long-running-tasks-de74825a6ae9): the approved spec appears on disk as `ORIGINAL_REQUEST.md` — "it was actually the software specification, albeit having a few differently structured details than the one presented as an artifact." [?]
**User's usage:** *Ignoring/bypassing.* The interview is designed for a human approver. If the primary agent answers it, the "Independent Verification" field — the only documented lever for rubric-based judgment of markdown deliverables — is the thing most likely to be filled in weakly. Nothing documents non-interactive approval.

### A3. Phase 2 — autonomous execution & the three artifacts [D]
TW: "Once approved, Sentinel hands off the project to the Project Orchestrator… Agents coordinate and share progress using structured artifacts in the workspace:
* **Request artifact**: Captures your initial prompt, goals, constraints, and testable acceptance criteria.
* **Project plan artifact**: Tracks the milestone roadmap, active workstreams, and dependency flow.
* **Progress artifact**: Records live milestone status and completed tracks."
And: "Every state change, command run, review comment, and verification log is recorded in the project plan and progress artifacts, alongside conversation logs. You can monitor live progress across agent tracks in the UI subagent panel or CLI status bar." CLI: "inspect milestone progress in the project plan and progress artifacts in real time."
**No paths, filenames, or schemas are documented anywhere.** [C] Observed filenames: `ORIGINAL_REQUEST.md`, `PROJECT.MD` ("used by the project orchestrator to track the feature set and the milestones… 6 feature milestones and 1 final milestone") — Medium [?]. Forum (June 5, https://discuss.ai.google.dev/t/the-teamwork-preview-slash-command-working-not-working/169343): "Dozens of Markdown files dumped straight into my agent's working directory… ~50 Markdown files" — i.e. artifacts are plain markdown, not JSON, and (at that time) landed in cwd. See §B for how to read them.
**User's usage:** *Ignoring.* They want structured state but haven't located/parsed these; and since no schema exists, any parser must be per-run heuristic.

### A4. Execution paths / patterns and their prompt signals [D]
TW table (verbatim triggers):
| Path | Best for | Trigger |
|---|---|---|
| General (Distributed coding) | Multi-file SWE, refactoring, systems sim, research | *Default* |
| Iterative coding (lighter SWE) | "One self-contained change… This path cannot decompose the task." | "*keep it small*", "*keep it focused*" |
| Document Review | "Multi-angle critique and synthesis of papers, RFCs, and design docs." | "*review this paper*", "*critique this design doc*" |
| Math / Proof | proofs, bounds | "*prove theorem X*", "*verify mathematical bounds*" |
| Math / Proof (Large Team) | "High-scale tournament networks" | "*Use a very large team of agents*" |
B‑TW names five patterns: Iterative Coding, Distributed Coding, Long Proof, Self-Verification, Document Review; "Gemini analyzes your prompt and automatically selects the appropriate pattern"; "patterns are **adaptive at runtime**. The framework dynamically decides how many agents to spawn… Agent count and team structure can shift mid-run." Patterns grid SVG: Document Review = "Segment → Review → Synthesis"; Distributed Coding = "Explore → Critic → Verify".
**Team sizing signals:** only two documented — "keep it small/focused" (forces non-decomposing Iterative path) and "Use a very large team of agents" (math only). No numeric knob.
**User's usage:** *Misusing by omission.* An extraction prompt with no signal falls to Distributed coding (code-oriented Critic/Challenger/test evidence). For document work, the docs' fit is Document Review, but its trigger is *review/critique* wording, not extraction.

### A5. Roles — what each verifies [D]
TW (core): **Sentinel** "takes over once you approve the prompt… records your request, routes tasks, posts periodic progress updates, and spawns the Success Auditor before wrapping up." **Project Orchestrator** "breaks the approved brief into structured milestones, coordinates parallel work tracks, delegates every unit of work, and hands off to a fresh successor between milestones." **Explorers** "Read-only research agents… without modifying any source files." **Workers** "terminal and file tools to build components, refactor code, and write unit tests in focused, non-overlapping tracks."
TW (gates): **Critic** "independent code reviews, evaluating correctness, logical completeness, robustness, interface conformance, and adherence to project code style." **Challenger** "adversarial test suites, edge cases, failure-path probes, and worst-case inputs that stress runtime and memory." **Auditor** "Validates work against the selected integrity mode and checks test evidence against real command output, ensuring tests genuinely passed rather than being mocked or skipped." **Success Auditor** "runs a full end-to-end verification pass and must confirm everything works before Sentinel presents the finished project."
B‑OS adds a **Reviewer** ("design correctness, edge cases, and interface contract compliance") and describes the Auditor as "strict static analysis checks on the code to detect cheating… When the Orchestrator believes it has finished all milestones, a final audit is forced". Distributed-coding flow SVG: "Result Rejected → back to Sentinel → Orchestrator", "Ralph Loop ↻ Iterate until converge", Sentinel "Always active / Restarts orchestrators", Worker "Isolated branch".
[C] Medium observed names: "Multi-Agent Team Lead", "Core Implementation Worker", "Challenger Subagent", "Forensic Auditor Subagent", "Reviewer Subagent", "Victory Auditor Subagent" [?] — role names drift between runs.
**User's usage:** Their chain (Sentinel → Orchestrator → Explorers → Worker → review panel → Success Auditor) matches docs, but every verifier is defined in code terms (tests, runtime, memory, style). For markdown deliverables these gates have nothing to check unless Phase 1 defines a rubric-judging agent.

### A6. Integrity modes [D] — verbatim
| Mode | Purpose | Verification Behavior |
|---|---|---|
| `development` | Rapid iteration | "Lenient. Flags only fabricated outputs and facade implementations; code reuse, libraries and pre-built frameworks are all permitted. (Default.)" |
| `demo` | Reproducible presentation | "Moderate. Adds: no copying core logic from open source, no delegating core work to external tools, no reading test source to reverse-engineer expected behavior." |
| `benchmark` | Thorough evaluation | "Maximum strictness. Fully independent, from-scratch implementation; language standard library only." |
"if you rule out all four shortcuts, the run uses `benchmark` mode, and the Auditor enforces strict verification rules: disallowing mocked test passes, validating ground-truth evaluations against real system execution."
**Benchmark for documentation extraction?** No — every axis the modes control (copying OSS logic, external tools, reading tests, non-stdlib libraries, mocked test passes) is about *code implementation provenance*. For extraction, `benchmark`/`demo` would at best be no-ops and at worst forbid using parsing libraries/tools ("no delegating core work to external tools"). The only mode behaviour that matters for markdown output is `development`'s "Flags only fabricated outputs and facade implementations" — which is exactly the failure mode (hallucinated extractions) you want caught. **Verdict: `development` is correct; the fidelity lever is Phase 1 "Independent Verification… an independent agent judging against an explicit rubric", not the mode.**
**User's usage:** *Using correctly* (development), *ignoring* the rubric lever.

### A7. Safety / isolation features [D]
* **Project Working Directory** default `~/teamwork_projects/{PROJECT_NAME}` — "keeping your main repository clean". *User:* unknown whether overridden; if not, deliverables land outside the repo.
* **Exclusive File Ownership** — "the Project Orchestrator assigns specific files to individual Workers. Multiple workers never edit the same file at the same time." Applies *within* a team. *User:* five parallel teams have no cross-team ownership guarantee — collisions on shared paths are possible unless work units are disjoint dirs.
* **Per-Agent Scratch Directories** — "Each subagent has its own working directory and writes its helper scripts, notes, and logs there rather than in the project root." Location undocumented.
* **Worktrees**: BO comparison table: Teamwork = "Persistent isolated worktrees per milestone" vs Boost "Ephemeral isolated worktrees". SA `invoke_subagent` workspace options `inherit` / `branch` (isolated git worktree) / `share`. GHCL 1.1.26: worktrees live under `.system_generated/worktrees` and orphaned ones used to accumulate.
* **Self-succession** — B‑OS: "the Orchestrator tracks its cumulative subagent spawn count. Once it hits a limit, it dumps its complete state into handoff files, kills its own background tasks, and invokes a subagent with the same goals and permissions." TW: "hands off to a fresh successor between milestones to prevent context degradation." SVG: "Self-Succession Lead".
* **Watchdog cron** — B‑OS: "We use the new Scheduled Tasks primitive to set a background recurring cron that checks progress files that the various subagents contribute to, and if the timestamp has been stale for too long, the Sentinel terminates and respawns it." The underlying tool is `schedule` (HK: args `DurationSeconds`, `CronExpression`, `MaxIterations`, `Prompt`). [C] Medium confirms: "the Orchestrator Agent spins up cron jobs that monitors running subagents." Implication: progress files carry timestamps the watchdog polls — a machine-readable-ish signal, format undocumented.
* **Anti-cheat** — B‑OS: agents "were cheating by referencing the conversations from past runs that we forgot to clear" → "anti-cheating measures and guardrails". Relevant if 5 teams share `~/teamwork_projects`.
* **Machine awake** — B‑OS: "you will need to keep your machine awake throughout the duration."
* **Permissions** — B‑OS: "obey the same permissioning… you set for the project you invoke the agent team from"; SA: subagents inherit command prefixes, dir scopes, sandbox; "Permission Bubbling… bubbles up to the main UI/Subagent panel." MODES: `accept-edits` is inherited by subagents; TUI `always-proceed` auto-approves artifacts for subagents (CL 1.0.14).
**User's usage:** using all of these implicitly (they are automatic); not exploiting worktree isolation or the working-directory field deliberately.

### A8. Monitoring & control surfaces [D]
* `/agents` panel (AGP): rows show Identifier, Role, State (`running|done|error|killed`), Step; `Enter` = Subagent Detail View ("complete internal thoughts, tool calls, and execution stdout"); `K` kills "the highlighted running subagent… and all its child threads"; `A`/`D` inline approvals; groups "grouped by their triggering prompt"; nested subagents shown (CL 1.1.1, 2.1.4).
* `Alt+J` = `prompt.teleport_agent` "Instantly switches focus to the next subagent awaiting confirmation" (REF, CS); `Ctrl+K` = fast approve; `Ctrl+O` trajectory toggle.
* Stop semantics: "Stopping a subagent now also stops everything it spawned, including nested subagents and their background tasks" (CL 2.6.0, 1.1.10).
* "Continue" — B‑OS: "If the agent team stops in the middle due to lack of quota or credits, you can simply purchase more credits and then tell the team to 'Continue' and it will pick up where it left off." That is the *only* documented mid-run steering verb. General subagent steering (SA): "The parent agent can interrupt a subagent by sending a message or terminating it"; idle agents "automatically re-awaken… upon receiving a message"; "Agents can read each other's conversation transcripts." External steering: SIDE `agentapi send-message <conversation_id> <prompt>`.
* **Custom roles:** not documented. Patterns are "a specification rather than an executable program" selected automatically (B‑TW). Custom `.md` agents (SA) are for `invoke_subagent`; nothing says Teamwork consults them. [C] GH #555 (https://github.com/google-antigravity/antigravity-cli/issues/555): even plain orchestration "dynamically creates subagent instructions rather than loading pre-defined static definitions."
* **Hooks for team events:** no team-specific events. HK events: `PreToolUse`, `PostToolUse` (matcher on tool name — you can match `invoke_subagent|send_message|manage_subagents|schedule|define_subagent`), `PreInvocation`, `PostInvocation`, `Stop` (has `fullyIdle`: "true if the agent is completely finished and all background commands or asynchronous tasks have completed"). [C] GH #809 (https://github.com/google-antigravity/antigravity-cli/issues/809, open, Aug 17): "PreToolUse/PostToolUse fire for its tool calls with no field identifying the agent context" — no `subagentId`/role; whether hooks fire inside subagents is undocumented. GH #640 (https://github.com/google-antigravity/antigravity-cli/issues/640): PreToolUse `block` ignored for `invoke_subagent`.
* **Headless stream:** see §B.
**User's usage:** *Ignoring* `/agents`, Alt+J (irrelevant if headless), hooks, sidecar `agentapi`.

## B. STRUCTURED STATE — exactly what is machine-readable

### B1. Teamwork artifacts on disk
* **Documented:** request / project-plan / progress artifacts "in the workspace"; default workspace `~/teamwork_projects/{PROJECT_NAME}` (TW). Format: markdown (forum, Medium) [C]. Names observed: `ORIGINAL_REQUEST.md`, `PROJECT.MD` [C][?]. Progress artifact name: unobserved; the watchdog polls its timestamp (B‑OS), so mtime is a usable liveness signal even without parsing.
* **Schema:** none. Treat as free-text markdown; parse milestone checkboxes/headers heuristically, or simply surface `mtime` + line count per team.
* **Practical read path for a statusline/external tool:** `find ~/teamwork_projects/*/ -maxdepth 1 -name '*.md' -newer …`; tail `PROJECT.MD`; watch mtimes. All [C]/heuristic — no [D] contract.

### B2. Transcripts (JSONL) [D]
* Path: `<app_data_dir>/brain/<conversationId>/.system_generated/logs/transcript.jsonl`, `<app_data_dir>` = `~/.gemini/antigravity` (2.0) / `~/.gemini/antigravity-cli` (CLI) / `~/.gemini/antigravity-ide` (IDE) (HK common fields; https://antigravity.google/docs/ide/hooks). Also `artifactDirectoryPath` = `<app_data_dir>/brain/<conversationId>`.
* Subagents: "Historical conversation transcripts remain readable in JSONL logs" (SA); the stream's `subagent_info.log_uri` points at each child transcript (HL). Subagent conversations are hidden from `/resume` (CL 1.0.6).
* Line schema of transcript.jsonl: undocumented.

### B3. Headless `stream-json` (the only documented per-subagent structured feed) [D]
HL: events `init` → `step_update`* → `result`. `step_update` fields: `conversation_id`, `step_index`, `state` (`ACTIVE|DONE`), `step_type` (`user_input|agent_response|tool|checkpoint`), `tool_name`, `text_delta`, `duration_seconds`, `usage` (`input_tokens, output_tokens, thinking_tokens, cache_read_tokens, total_tokens`), `tool_info` (`name, parameters, output, error{type,message}`), **`subagent_info`**: "Steps that spawn subagents carry `subagent_info` instead, listing each subagent under `subagents` (with `type_name`, `role`, `conversation_id`, `log_uri`, and `workspace_uris`)." CL 1.1.8: "so consumers can correlate child trajectories." CL 1.1.23: subagent trajectory metadata sent "once per subtrajectory instead of with every step."
`result`: `conversation_id, status (SUCCESS|ERROR|CANCELED|INTERRUPTED|INVALID|WAITING|RUNNING), response, error, duration_seconds, num_turns, structured_output, json_schema, usage`.
Caveats: only *spawn* events carry `subagent_info` — no documented per-subagent state transitions (running/idle/killed) in the stream; you derive liveness by tailing each `log_uri`. Slash commands "handled by the CLI itself" are rejected in `--input-format stream-json` (`/model`, `/usage`); `/teamwork-preview` is a prompt-expansion command (CL 1.1.9 "Slash-command expansion in print mode"), so `agy -p "/teamwork-preview …" --output-format stream-json` is the documented-adjacent way to get structured team telemetry — though Phase 1 needs turns (use `--input-format stream-json` to keep one process open and answer the interview).

### B4. Statusline JSON payload — complete documented field list [D] (SL)
`cwd`, `session_id` (alias), `conversation_id`, `transcript_path`, `model{id,display_name}`, `workspace{current_dir,project_dir}`, `version`, `context_window{total_input_tokens,total_output_tokens,context_window_size,used_percentage,remaining_percentage,current_usage{input_tokens,output_tokens,cache_creation_input_tokens,cache_read_input_tokens}}`, `exceeds_200k_tokens`, `product`, `quota{<bucket>:{remaining_fraction,reset_time,reset_in_seconds}}`, `agent_state` (`idle|thinking|working|tool_use|initializing`), `vcs{type,branch,client,dirty}`, `sandbox{enabled,allow_network}`, `artifact_count`, `plan_tier`, `email`, `pending_input_count`, `tool_confirmation_pending`, `task_count` ("Number of running background tasks"), `terminal_width`, `execution_mode` (`planning`, `fast`…), `vim{mode}`.
**Undocumented-but-real fields:**
* `cost` — CL 1.1.21 / GHCL: "Added a `cost` field to the status line data model, exposing the unrounded estimated cost of the current session" — **absent from the SL table** [D‑changelog].
* `subagents` — **not in SL**, but Google's own example script reads `(if .subagents | type == "array" then (.subagents | length) else 0 end)` (https://github.com/google-antigravity/antigravity-cli/blob/main/examples/statusline/statusline.sh, line 53) [D‑example]. The community plugin (https://github.com/weby-homelab/antigravity-cli-statusline) reads the same and adds a `/tmp/agy_subagent_truth` cache to suppress stale non-zero counts — i.e. it is treated as an array whose length is sometimes stale [C]. **Element schema is unknown**; nobody reads anything but `length`. Quota bucket ids observed by that plugin: `gemini-5h`, `gemini-weekly`, `3p-5h`, `3p-weekly` [C] (docs example shows only `gemini-weekly`).
* Effort: no field; encoded in `model.id` e.g. `"Gemini 3.5 Flash (High)"`.
**Is there a per-subagent list?** Possibly — `subagents` *is* an array — but undocumented and only its length is known to work. **Where to read live subagent status for "subagent rows":** (1) dump the raw payload once (`"command": "tee /tmp/sl.json | your.sh"`) and inspect `.subagents[]`; (2) otherwise, `stream-json` `subagent_info.subagents[]` + tail each `log_uri`; (3) `/agents` panel is the only documented live view. Note the statusline fires "Whenever the agent state changes" **for that TUI process only** — it cannot see five headless team processes.

### B5. Other structured surfaces
* Hooks stdin (HK): `conversationId`, `workspacePaths`, `transcriptPath`, `artifactDirectoryPath`, `modelName`; `PreToolUse.toolCall{name,args}` — for `invoke_subagent` the args are `Subagents[{Prompt,Role,TypeName,Workspace}]`, which is the richest documented per-spawn record (role + prompt). `Stop.fullyIdle`. No parent/child linkage (GH #809).
* `manage_subagents` tool (`list|kill|kill_all`, `ConversationIds`) and `manage_task` (`list|kill|status|send_input`) — agent-side, not exposed to scripts.
* Print-mode read-only commands: `agy -p "/usage"`, `/quota`, `/credits`, `/model`, `/effort` emit TSV or `--output-format json` "without starting an agent turn, spending quota" (CL 1.1.11/1.1.12) — good for quota rows.
* Sidecars: runtime data `~/.gemini/antigravity/sidecar_data/<id>/{data,logs,events}`; `events/` = "JSON files recorded for agentapi calls" (SIDE).

## C. BOOST

**What it is [D]:** BO: "an on-demand multi-agent reasoning pipeline designed for challenging software engineering tasks… breaks down the problem, delegates focused workstreams to specialized subagents, and independently verifies solutions across iterative rounds." SA/SC: "three-tier multi-agent reasoning hierarchy (`Orchestrator` -> `DeepCoder` / `DeepInvestigator` coordinators -> isolated execution workers)". Phases: (1) Primary Orchestrator "inspects workspace context, and formulates an execution strategy"; (2) "Implementation workstreams… Investigation workstreams… without modifying files… Local verification"; (3) "validates the combined solution against full test suites and edge cases. If an assertion fails, error diagnostics are fed back". Shipped in Antigravity 2.0 **2.12.0 (Sep 2 2026)** "to enhance thinking effort by using a multi-agent reasoning pipeline"; CLI earlier (1.1.25 fix "Fixed `/boost` failing at runtime by improving worker tool configurations"). Plan: BO/SC say "paid plans"; SA says "Google One AI Premium (Pro and Ultra tiers) and Enterprise" — inconsistent wording [D].

**Boost vs Teamwork — the docs' own table [D] (BO):**
| | Default | Boost | Teamwork |
|---|---|---|---|
| Focus | interactive coding | "Deep reasoning and tricky bugs" | "Autonomous multi-day agent teams" |
| Horizon | seconds–minutes | "Seconds to hours" | "Hours to days" |
| Scoping | single prompt | "Immediate execution" | "Two-phase scoping interview" |
| Architecture | single loop | "3-phase reasoning hierarchy" | "Multi-role agent teams" |
| Workspace | shared tree | "Ephemeral isolated worktrees" | "Persistent isolated worktrees per milestone" |
| Verification | single pass | "Multi-round independent verification" | "Adversarial falsification and independent success audit" |
| Best for | features, nav | "Tough concurrency bugs, algorithmic optimization, intricate multi-file refactors" | "Subsystem builds, formal proofs, and autonomous OS-scale campaigns" |
BO: "`/boost` addresses the crucial middle ground… without requiring complex setup or prolonged scoping interviews." SC selection guide: "Complex bug, race condition, or algorithmic puzzle → /boost"; "Multi-day project, repository migration, or research → /teamwork-preview". Boost has **no** request/plan/progress artifacts, integrity modes, Sentinel, or Success Auditor documented; all four documented use cases are code (concurrency, algorithms, refactoring, root-cause).
**Cost guidance:** none quantified for Boost [D]. [C] AlphaSignal: "no separate per-call price, but the token spend is meaningfully higher… orchestration plus multiple subagents plus verification rounds" (https://alphasignal.ai/news/google-antigravity-s-boost-turns-hard-bugs-into-multi-agent-reasoning-missions); explainx: "budget for 3–10× normal token burn" [?] and two pipeline modes "complex implementation" / "root-cause investigation" attributed to the @antigravity Sep 1 thread [?] (https://explainx.ai/blog/google-antigravity-boost-deep-reasoning-command-2026). Community comparison experience is thin (Boost is 2–3 days old in 2.0).

**Decision rule** *(researcher's original — superseded by "Position after review" at the top of this file where they differ)*
* **(i) Parallel mechanical extraction over many files → neither. Use `invoke_subagent` fan-out from the primary agent** with a custom `.md` agent (`model: flash`, read-only `tools` + `write_to_file`, `subagent: true`), one subagent per disjoint file set (docs best-practice; SA "A parent agent can invoke multiple subagents concurrently"; MODES `accept-edits` inherited). Cheapest, no Phase‑1 interview, no 8-role overhead ×5. Add a single *judge* subagent per batch with an explicit rubric if you want the "independent agent judging" property. Reserve Teamwork **Document Review** ("review this…/critique this…") for the synthesis/critique stage only.
* **(ii) Single complex judgment task → `/boost` if it is code-shaped and test-verifiable** (its verification loop needs tests/benchmarks); if it is a non-code analytical judgment, Boost is off-label — use Teamwork *Iterative* ("keep it small") or *Document Review*, or a single Pro/high-effort agent with `/plan`/`/grill-me`.
* **(iii) Long multi-day build → Teamwork**, one team, human-run Phase 1, `demo`/`benchmark` only if provenance matters; expect "Continue" after quota stops.

## E. GAPS AND MISUSE — ranked by impact

1. **Wrong granularity for mechanical extraction (cost ×~8 roles ×5 teams)** *(corrected: Teamwork is the right mechanism at project/phase level; the defect is one team per unit — see "Position after review")*. Teamwork is documented for multi-day SWE/research (TW, B‑TW "overkill for everyday tasks" per [C] explainx); docs prescribe subagent fan-out for sweeps (cli/best-practices). Each team spawns Sentinel+Orchestrator+Explorers+Workers+Critic+Challenger+Auditor+Success Auditor and code-oriented gates that have nothing to verify in markdown. Fix: §C(i).
2. **Undocumented programmatic dispatch / bypassed Phase 1.** No `teamwork_preview` tool exists (HK tool list); the interview and "approve execution with a single confirmation" are human-facing (TW). Agent-answered interviews are unsupported, and likely under-specify "Independent Verification" and "Acceptance Criteria" — the only levers that produce rubric-judged markdown. If you keep Teamwork, write those two fields explicitly in the invoking prompt.
3. **Pattern selection left to default.** No signal ⇒ Distributed coding (code Critic/Challenger). For document work use "review this…/critique this…" (Document Review) or "keep it small" (Iterative, non-decomposing) (TW table).
4. **Structured-state expectation vs reality.** Progress/plan artifacts: no paths/schemas (TW); observed as free markdown `PROJECT.MD`/`ORIGINAL_REQUEST.md` [C?]. Statusline: no documented per-subagent list; `.subagents` array undocumented and stale-prone [C]; `cost` undocumented in SL; statusline is per-TUI-process. Only documented structured child telemetry is `stream-json` `subagent_info{type_name,role,conversation_id,log_uri,workspace_uris}` (HL) — run teams headless to get it.
5. **Cross-team collisions and anti-cheat.** Exclusive file ownership is *intra*-team (TW); five teams under one primary agent share `~/teamwork_projects` and the primary's cwd; B‑OS documents agents "cheating by referencing the conversations from past runs." Give each team a disjoint working directory in Phase 1 field 5.
6. **Primary-agent context pollution and blast radius.** Sentinel "posts periodic progress updates" to its parent (TW); with 5 teams the primary's context fills; stopping the primary "stops everything it spawned" (CL 2.6.0). Consider a thin dispatcher that only tails artifacts.
7. **Quota exhaustion mid-run with no pause.** B‑OS Flash+Ultra warning; forum reports of hard stops; only recovery is credits + "Continue". Five concurrent teams multiply the 5‑hour burn and hit the undocumented concurrent-stream limit (CL 1.1.21). Set `useG1Credits`/"Always" deliberately or don't.
8. **Integrity mode:** `development` is right; `benchmark` is code-only semantics (TW) — not a fidelity control for extraction. Don't switch; instead add "independent agent judging against an explicit rubric" in Phase 1.
9. **Hooks won't give you per-agent telemetry.** No agent identity on subagent tool events (GH #809); `PreToolUse` can't gate `invoke_subagent` (GH #640); hooks that call a model time out (CL 2.6.0). Use `PostToolUse` matcher `invoke_subagent` to log `Subagents[].Role/TypeName` at spawn time — that is the best documented hook-side record.
10. **Preview-grade reliability.** Repeated availability breaks (CL 1.1.17, 2.6.0, forum July outage), moderator advice "keeping regular backups… such as using Git" (https://discuss.ai.google.dev/t/is-there-an-easy-way-to-rollback-the-teamwork-preview-modification/174763), enterprise/GWS gating (#469). Keep deliverables under git.
11. **Model mixing not available in Teamwork yet** (B‑TW "upcoming updates"); subagents inherit the invoking model — pick Flash at the primary or the whole team runs Pro.
