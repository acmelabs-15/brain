# RES-098: Every form a wait takes, and where one crosses a file

## Question
Which forms does a wait take everywhere, and where does one cross a file: Blocked by, blocking links, depends on, sources, supersedes, prose waits, cycles and the frontier?

## Answer
Sufficient answer: with a source per claim, across code, instructions, tests, evals, docs and real records, the record gives a catalog of every form of wait or link. For each form it states where it is defined, who writes it, what checks it, what reads it, and whether it is a wait or only a link. It states what ends each wait today in each code path and each instruction, and where those disagree. It states how cycles, missing targets and self-links are handled for each form. It lists every wait that crosses a file or an effort today. It states what DEC-029 decided and rejected, and the facts for IDEA-016 rows 01, 04 and 10. It names what could not be established and any contrary evidence.

The record meets this condition, with the limits under "What could not be established". Each claim below has a finding under Findings, named by its label (A01, B03 and so on). Words used here. A wait: an item cannot start, or cannot finish, until another thing happens. A link: one item names another item, and no work waits on it. A form: one way to write a wait or a link down. GLOSSARY.md has no entry for a wait or a link; see Follow-ups. The forms have numbers. Forms 1 to 47 keep the numbers of the first version, forms 48 to 74 came with the second version, forms 75 to 90 with the third and forms 91 to 105 with the fourth, so the numbers in one catalog do not run in order.

### Summary
- Brain's code reads one form of wait between two rows: a two-digit row number in the Blocked by cell of a map row or a plan row. The number names a row of the same table. No other wait of one item on another item is a field (A01 to A06, D-group).
- Code also reads waits that are not between two rows. An idea cannot be `done` or `specced` while a row is still to do, while fog is left, or while its Intent has no confirmation line. A map row cannot be `resolved` until the record in its Result exists and is valid. A spec is not finished while a plan row is still to do. A research record with `outcome: blocked` shows in the report. The migrate mode of setup holds back the `layout: 2` marker while a file waits for a commit by the user (B13, B19, B21, E04, E22, J22).
- The status of a blocker ends a wait in two different ways, by code path. For a row that waits on a row, only `resolved` ends the wait, and a `superseded` blocker is an error that a person must repair. For an idea or a spec that waits on its own rows, `resolved` and `superseded` both end the wait. The checkpoint rule drops a superseded row and its edges (B01 to B07, B19 to B22).
- The end of a wait is not final in the instructions. interview-me replaces a resolved row when changed evidence invalidates it, and it opens a row again when its record does not settle it. The dependents are reviewed by hand, and no check names a row that already started behind such a row (J02, B10).
- Each of the nine real specs holds a free-text `Status:` line in its body, and no code reads it. So the state of a spec that blocks reads three ways: its own line ("draft for review" in four specs), the word "built" in the plan head of the module that waits, and the code's "finished" (J19).
- The paths disagree in seventeen places, listed below. Four matter most. Wave 1 of `brain plan` holds rows that are `in-progress`, and five instruction sites call wave 1 the frontier. No rule compares a row's own status with its blockers. The build never writes `in-progress`, although the values and the report name it. `superseded` has three different effects (B08 to B11, B22).
- Nine stored forms link one item to another: `superseded by NN`, `superseded by DEC-NNN`, the Result cell, `result:`, `sources:`, `from:`, `evidence:`, `spec:` and the heading of a todo block. Two of them gate a status: a map row cannot be `resolved` without a valid record in its Result, and an idea cannot be `done` without `result:`. No work waits on the other seven. `brain check` checks that the target exists for the first five, but not for a plan row's Result or a commit SHA. It checks only the shape of `from:` and `evidence:`, and it checks that `spec:` equals the file's ID (C-group, D-group, J36).
- A cycle is found only between rows of one table. A row that names itself is a cycle of one row. A decision record can supersede itself, and two decision records can supersede each other, with no finding. One finding can hide another: a cycle hides each superseded-blocker finding, and in a plan one row problem hides every later check (C01 to C09, C16).
- Every wait between two efforts, or between rows of two files, is prose. This repo holds 2 row-to-row waits between ideas, 2 waits between efforts, one wait of an idea's spec on a pull request of another spec, one stated order of 8 ideas, 11 stated waits between modules in DEC-004 and the spec files, 5 decisions that leave a point to a row, and waits in older records on an idea that is not in this worktree and in no commit. Another worktree of this repo holds that idea, and there its row 15 is `resolved`. Some prose waits name a target that is not an item: a pull request merge, a release, a later ask to the user. One fixture of the current layout holds a parked idea with the note "dark mode first" (F-group). The third pass added ten more waits from the checked topic records, X18 to X27 (H-group). The fourth pass added X28 and X29; X29 is the one wait across files that code works out (J14, J22).
- No shipped instruction, template or command names a place for a wait on another idea or on a row of another file. The places in use are each writer's practice (J16).
- Five stored values hold a wait on something that is not a row: `status: proposed` on a decision record, `outcome: blocked` on a research record, `status: parked` on an idea, the confirmation line of an Intent, and the row type (a decide type or `checkpoint`). Four real ideas are `parked` today. The key `decided:` of a decision record stores the end of a wait on the user, and who ended it. Other waits on the user are prose or chat: the protocol puts them "in the active effort's rows and records", and three more texts name another place (E-group, J05, J26).
- DEC-029 chose a "blocked by" property in the frontmatter of each idea and spec, which names ideas and specs. The spelling `blocked-by` is the agent's proposal. It rejected two options: a Blocked by cell that names another effort's row, and the option of no new field. The user's answer did not speak about the cell form. Where the paths disagree:
1. **The frontier and wave 1.** `frontier` takes `open` rows only. `layWaves` also puts an `in-progress` row in wave 1. The build command in its two copies, the incremental-implementation skill and the planning skill (twice) say that wave 1 is the frontier. The two agree only while no plan row is `in-progress`, and the build keeps a running task's row `open` (B08, B09).
2. **A row's status against its blockers.** The frontier rule governs which row to take next. The whole-map pass may resolve any open row that an existing answer settles, and its condition is "its required inputs hold". No check reports a row that is `in-progress` or `resolved` while a blocker is not resolved. One live case exists: IDEA-016#28, #29 and #30 are `in-progress` while each of their 11 blockers is `in-progress` (B10, B11, B23).
3. **`in-progress` on a plan row.** The value is defined and the report lists rows in progress. The build writes only `resolved`. An eval grader accepts a checkpoint that is `open` or `in-progress` (B09).
4. **A superseded row has three effects.** The table below gives them. The header of `graph.ts` and one fixture README say a superseded row "drops out". That holds for the second and third effect, and not for the first. interview-me tells the main session to repair the link, and one eval fixture holds the unrepaired state on purpose (B04, B05, B19 to B22).

   | Code path | Effect of a superseded row |
   |---|---|
   | `frontier`, `layWaves`: a row waits on a row | It holds each waiting row. `brain plan` and `brain check` report it while the waiting row is `open` or `in-progress` |
   | `ideaCompletionProblems`, `effort.ts`: an idea or a spec waits on its rows | It counts as settled. The idea can be `done`, and the spec is finished |
   | `checkpointProblems`, `overlaps`: the phase and its checkpoint | It drops out of the graph. A dependency path through it ends |

5. **A superseded record.** A decision record that is superseded later still counts as the Result of a resolved row. A superseded row never counts for a row that waits on it (B14). ### Facts for the decide rows
These are facts. They are not a recommendation. Row 31 joins them with the other topics.

**Row 01: when does a named item stop blocking another?**
- Today two rules exist, by the kind of wait. For a row that waits on a row, one value ends the wait: the blocker row is `resolved`. For an idea or a spec that waits on its own rows, two values end it: `resolved` and `superseded`. DEC-051 renames `resolved` to `done` (B01, B02, B06, B19, B21).
- For a row that waits on a row, `superseded` never ends the wait. It is an error in `brain plan` and `brain check` while the waiting row is `open` or `in-progress`, and the code does not follow the link to the replacement. The instruction is a hand edit: point the wait at the replacement, or remove it with a reason (B04, B05, B07).
- In the real maps, 5 rows are superseded, and 4 of them have more than one replacement, while `superseded by NN` names one row. The waits on those 4 rows were moved by hand to a different row, row 31 (B25).
- The checkpoint rule ignores a superseded row and its edges (B22).
- A superseded row can keep its Result and its own Blocked by cell. A fixture holds both cases (B27).
- A row cannot hold `parked`: the row status pattern refuses it. Four ideas are `parked` today. Three of them hold open rows and a note that the idea "waits until he evaluates it". One was emptied by a split. No stored wait names an idea or a spec, so no rule exists for a wait on a parked item. The code tests only whether an idea's status is `define`, so a parked idea is "finished" (E05, E21).
- A spec has no status in its frontmatter, and no code reads one. Each of the nine real specs holds a free-text `Status:` line in its body: four say "draft for review", four say "approved", and one says "superseded" by DEC-002. The code calls a spec finished when no plan row is still to do, and also when it has no plan row at all. "Finished" is no evidence that the spec is built: SPEC-007 reads as finished and is not built. So the state of a spec that blocks reads three ways: its own line, the word "built" in the plan head of the module that waits, and the code's "finished" (B21, F16, J19).
- The end of a wait is not final today. By instruction, changed evidence that invalidates a resolved row gets "a replacement question", and the main session reviews "its dependents"; on resume, a row whose record does not settle it is opened again; a confirmed Intent loses its confirmation line when the intent changes. The code has no rule for a row that already started or resolved behind such a row, and it works out no list of dependents. In one real case the fixes after a review became new tasks, and no finished task was opened again (J02, B10, C16).
- A plan row is done only after verification and a review, not only after its commit: "Declare the task done only after the review passes". A draft decision in another worktree, DEC-023, makes the same point a rule for waits: a task that fails its review "stays unresolved, so the tasks blocked by it do not unblock" (J27, J20).
- No check ties `status: specced` to a spec. An idea can store `specced` while no spec lists it in `sources:`, and a spec can list an idea that is still `define`. RES-037 names the first fault (J04).
- The user's reference board ends a wait on four status words: done, closed, resolved or complete. "In Review" does not end it. A blocker that is not on the board counts as open, with no error. The file is evidence, not a decision (J01).
- An accepted decision gives a spec the worked-out states "Not planned (no rows)" and "In review (a checkpoint row is in progress or next)". Today the code calls a spec with no row finished, and the build never writes `in-progress` on a checkpoint row (J28, B09, B21).
- The standing preference of IDEA-015 and IDEA-016 uses "park" for a row: "Ask rows that do not wait on research, and park the ones that do." DEC-051 gives `parked` to every item and says that waiting is never stored (J30).
