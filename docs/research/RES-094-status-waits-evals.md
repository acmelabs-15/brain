Three properties of the regex graders matter for a format change:

1. They match by column position, and they differ in how far they count.

   | Grader | Cells it counts | A new or moved column breaks it when it is |
   |---|---|---|
   | `plan-rows-resolved`, `rows-resolved` | Six: number, name, Type, Status, Blocked by, Result | Before Status, between Status and Result, or when Blocked by is removed. A column after Result breaks neither |
   | `stops-at-checkpoint`, `rows-in-progress` | Four, up to Status | Before Status only |
   | `plan-file` | Three, up to Type | Before Type only |

2. The two six-cell graders skip the Blocked by cell with `[^|\n]*`. So any text in that cell passes, and no grader fails when the form of the cell changes.
3. They hold the status words as literals: `resolved` in four graders, `in-progress` in two and `open` in one (`stops-at-checkpoint`, twice). They also hold the type words `task`, `checkpoint` and `research`.

The start graders have a recorded limit. IDEA-001 row 19 says: one worktree made from the branch satisfies all five, and a sub-agent's `git merge --ff-only` counts as a merge.

The eval host limits what a session can do.

- Brain CLI: `brain check` and `brain status` (each with or without `--json`), `brain --help` and `brain new-doc IDEA|DEC|RES`. It does not allow `brain plan` or `brain new-doc SPEC`.
- Writes: Markdown files directly in `docs/ideas`, `docs/decisions` and `docs/research`, and `GLOSSARY.md`.
- Setup profile (keystone cases 2 and 3 only): also the three `docs/agents` files, and bounded calls of the setup writer and the capabilities script. The writer's allowed flags hold no `--migrate`, so this host cannot run a migration.
- Stop reasons: `next_question_observed`, `unexpected_question`, `harness_timeout`, `model_error` and `result_observed`. The doc says an unexpected question, error or timeout "is not an interview success".

So a session in this evaluation cannot write a spec folder, a plan row or a spec's frontmatter.

### What must be true before a change counts as done
`docs/maintainers/changes.md` applies when a skill, command, agent, setup rule or host adapter changes. Its rules that touch evals:

1. Trace the behavior from its host entry to its owner, and list the affected checks. Record any surface that does not apply, and why.
2. Implement at the owning source. Reconcile command behavior, router entries, skill metadata, host flags, human docs and installation behavior "in the same change". This rule decides whether scaffolds, graders and checks change together with the format.
3. Verify observable behavior at the public boundary. Static checks, host validators and model evaluations each cover a different thing; state each limit separately. "A native dialog check requires a submitted answer followed by the expected next prompt." That sentence is the contract's rule for evidence of a wait on the user.
4. For a skill behavior change, compare the old and the revised bundle with the official creator's evaluation loop. Keep prompts, versions, traces, artifacts, grades, budgets and user feedback. Generate the review viewer. Prepare concrete fixtures, and ask for any missing authorization for an external run before sending them.
5. For a code slice, run its touched tests, typecheck, lint, format check and the affected checks. "For text, run the checks that consume that text": a grader file and a scaffold are text that the dry checks consume. After integration, run the full `bun run check` and `bun run validate` once. Repeat a check after a change that can affect its result.
6. Review the diff and follow the commit contract. Add a Changeset for a user-facing change. Publication needs the user's authorization.
7. Record the actual commands, outcomes and limits.

Two more steps of that contract are about authoring, not about evals: load `skill-creator` and use `writing-for-agents` for skill text, and ask only through `ask-user-question`. They apply when a status or waits change edits a skill.

`docs/evals/interview-recovery.md` sets the rules for the interview evaluation:

1. Two complete plugin folders, a baseline and a candidate. Neither changes during a run. Record each repair of the baseline beside the result.
2. Run the first pair, and inspect its events before the other cases.
3. Grade against the events and the files saved before each question, not only the last snapshot. Use the official skill-creator grading schema and its review viewer.
4. A harness stop is not a user refusal or approval. Record native dialog rendering, long waits and real parallel worker timing as unverified.
5. A keystone run needs `approved: true` after a scoped approval, a budget ledger, and at most $1.50 and 480 seconds per process. A changed candidate source refuses the run; rebuild and review first. A repeated output folder is refused.
6. Before a keystone run, run `keystone-preflight.ts` and keep its output with the run.

`docs/evals/first-run.md` is a dated report of 2026-09-19. It sets no rule. It records why the plugin-eval cases cannot observe a wait on the user, and that the threshold check passes at 0.85.

No rule in these docs requires a run of the plugin-eval suite (`claude plugin eval`) before a change is done. Rule 4 above does require the creator's evaluation loop for a skill behavior change, and that loop needs model runs and their authorization.

Rules that the code enforces, outside those two docs:

- `bun test` runs every dry check. The CI workflow runs `bun test` on each pull request and each push to main, so a scaffold that no longer passes `brain check` fails CI on the pull request.
- The dry checks read each computed grader from `evals/` and apply it to a played run that passes the real `brain check`. So CI shows a mismatch between a computed grader and the format that `brain check` enforces.
- CI does not show a mismatch between a grader and what the skill text tells the model to write. The played runs hold their own literals (` resolved `, ` in-progress |`). Only a model-calling run shows that mismatch, and every judge grader, and every interview or keystone expectation.
- `suite.test.ts` holds the list of case names. A new, renamed or removed case fails it until the list changes. Each case needs a prompt and one computed grader.
- The Evals workflow runs the model-calling suite by hand or each Monday. No push triggers it. The threshold check fails a case whose score is under the threshold, 0.85 by default; a hand run can set another value.
