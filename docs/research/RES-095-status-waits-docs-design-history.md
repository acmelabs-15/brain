### Summary
- The glossary names status values for one item kind only: the idea (define, specced, done, parked). It uses the words status, open, resolved and block for rows but defines none of them. It has no entry for wave, blocked by, result, outcome, or any decision or research status (F02, F06, F08, F12, F14).
- README.md names no status value. It says where status handling lives: the workspace document, a thin `status` command and the session-start hook (F22 to F27). It says that model evaluations run by hand or weekly, outside `bun run check` (R12).
- docs/maintainers/changes.md is the gate for a change to instructions. It has seven steps. It names skills, commands, agents, setup rules and host adapters. It does not name the record format, the schema, the glossary or a migration (F28 to F38).
- docs/intent/workspace-and-stateful-interview.md is the design source of today's model. It was written on 2026-10-29 and last changed that day. It gives a reason for most rules (table "Design reasons"). It contradicts the current behavior in 16 places (table "Contradictions"). Eleven come from release 0.13.0. Three were there on 2026-10-29, where a template or a draft block was not changed when a later Decisions row or the code changed the rule (C01, C13, C14). Two are mixed (C11, C12) (H29).
- The design prefers a state that is worked out to a state that is stored, but it does not hold this rule everywhere. Worked out and never stored: the frontier, an idea's list of specs and the status report (F53, F74, F80). Worked out, then stored, then kept in step by a check: the Parallel waves section of every plan (R01). Stored with no check in `brain check` against the data that gives it: the idea status specced, and the ticks in todo.md (R02, O12; a search for tick and for a box pattern in scripts/workspace/check.ts finds no line).
- Two stored states were removed. The docs/STATUS.md note went because it was "not an accurate snapshot of the actual status" (C08). The spec index State column went with the move to spec folders; the commit gives the reason: "it indexed the specs that moved, and brain check refuses it in specs/" (H27).
- Since release 0.13.0 a row has a third home for state, in prose: the idea's Notes section holds partial answers, pending questions and waits with a retry condition, and a research record's Next action holds the blocker and the retry condition. No code reads either (R07, R08, C15).
- History has three steps. On 2026-09-19 status came in as hand-written forms in Brain's own records, in the first commit, and then as vendored forms: checkboxes, ADR status lines, and Brain's own ticket `Status:` and `Blocked by:` lines (H24, H01, H04). On 2026-10-29 the workspace design replaced them with frontmatter status and the row table. On 2026-11-05 release 0.13.0 added the research outcome, stricter checks, prose state in Notes, and a status report worked out from rows only (table "Order of change").
- The current tree still holds older ways in 33 migrated files, in prose status lines that are stale, in ticked boxes, in a retired status note, and in three name forms for the old layout (`layout-0.8`, `migrate-08`, `old-layout`) beside the marker value `migrated: 0.8` (table "Older ways in the current tree").

### README.md and the change contract
README.md describes no status value and no wait format. It gives four facts: the hook gives each session "the computed workspace report" (line 48); there is a thin `status` shortcut among ten commands (line 49); "Session state and recovery live in `docs/agents/workspace.md`" and "there is no separate status skill" (line 80); `bun run check` includes the workspace check (line 119). Its Lifecycle table lists the six stages and three more rows under the heading Stage (lines 64-74).

README.md also states where model evaluation runs (R12). The cases under `evals/` run with `claude plugin eval`. `bun run evals:gate` exits 1 "under the threshold, 0.85 by default". "The `Evals` workflow runs the suite by hand or weekly, never on every push". "Every run is model calls on the account that runs it." So `bun run check` holds no model evaluation. README.md:112-113 sends a maintainer to the change contract "before changing a skill or host behavior".

What docs/maintainers/changes.md requires (F28 to F38). The contract applies "when adding, renaming, removing or changing a skill, command, agent, setup rule or host adapter". A change to the stored status values or to the form of "blocked by" touches skills, commands and setup templates, so these steps apply to those parts:
