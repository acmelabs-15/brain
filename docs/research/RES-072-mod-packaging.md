# RES-072: How a plugin ships a mod

## Question
How does a plugin ship a mod, can one Brain mod serve both IDEA-013's opening question and a set of views, and does a marketplace install load it?

## Answer
The sufficient answer has five points, for IDEA-015#12 and the spec's architecture. The docs, the type file that Claude Code 2.1.330 writes, and local runs with throwaway `--plugin-dir` mods answer all five. RES-040 covers the guard, `allowManagedModsOnly`, `--bare`, `--safe-mode` and `disableAllHooks`; this record does not repeat them.

1. **Where a plugin declares its mod.** The `modules` key in `hooks/hooks.json` names the hooks module, as a list with one path relative to that file. A `modules` key in the file that `plugin.json`'s `hooks` field names also loads. A plugin has one hooks module: a second entry in the list, or a `modules` key in both files, is refused, and then no module loads. Brain's `plugin.json` already names `scripts/hooks/claude-code.json` for its classic `SessionStart` hook. A new `hooks/hooks.json` with `modules` loaded beside that file, and both the classic hook and the mod ran. So one Brain plugin ships one Brain mod, and every mod feature lives in that one module.
2. **Runtime and data.** Installed mods run in one shared worker thread, each in an environment of its own, with no Node.js APIs and no `Bun` global. Claude Code loads `.ts` directly, with no build step. The module imports plugin files by relative path, also outside `hooks/` and also extensionless, as Brain writes its imports. Brain's pure parsers load: `map.ts` with `schema.ts` and `lib/table.ts` parsed IDEA-015's 16 map rows in the mod. But a file that imports `node:*` stops the whole module, and a call into `Bun.*` fails at run time: `readFrontmatter` gave "Bun is not defined". 8 of the 11 source files in `scripts/workspace/` import `node:` modules, `status.ts` among them. So the mod gets workspace data from `$.process.run(["bun", $.plugin.root + "/scripts/brain.ts", "status", "--json"])`. That call gave exit 0 and 16,464 bytes of valid JSON in 53 to 64 ms, from the root and from a subfolder, in `-p` and interactive runs. Limits: the hook's own time is 10 seconds; `$.process.run` has a 30-second default timeout, 10 minutes at most, 4 MiB of `stdout`, no shell, and needs `bun` on Claude Code's `PATH`; `$.fs.read` reads 4 MiB per file.
3. **One mod for both.** Yes. In one interactive run, one `session.start` hook registered two commands and opened a question through `$.ui.ask` without waiting for it; the hook settled in 61 ms. The answer came back, and then both commands ran, one of them `brain status --json`. No rule forbids this, and the one-module rule requires it. The rules that shape it: a `$.command.register` that throws skips the rest of the hook, so register in `try` or before other work; the first prompt waits for `session.start`, so do not wait there for the question or for process work; a command name has letters, digits, `_` and `-` only, so no `brain:` prefix; a built-in name such as `status` is refused. A command the mod answers with text started no model turn in the `-p` runs.
4. **Marketplace install.** The docs say yes: a mod installs as a plugin from a marketplace, mods are on by default from v2.1.287, and the mod loads at the next start or after `/reload-plugins`. The user gives no approval for it apart from the folder's trust prompt; the hot-reload question is only for a mod that Claude writes in a session. Claude Code copies a marketplace plugin into `~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/`, so every file the mod imports or runs must sit inside the plugin, and `$.plugin.root` names that folder. Differences from `--plugin-dir`: no reload on save, no type files, load errors only in the debug log, and an edit needs a new version. A `--plugin-dir` copy with the same name replaces the installed plugin for that session. On this machine, the marketplace mod `cache-tax@claude-code-mods` wrote its `$.store` file today, so an installed mod ran here. UNVERIFIED: a Brain mod from the acmelabs marketplace loads the same way, because the brief forbids an install. UNVERIFIED: a project-scope install loads a hooks module after the trust check as a user-scope install does; the docs list limits for repository plugins (MCP approval, MCP bundles, monitors) and name none for a hooks module.
5. **The session's project folder.** `e.cwd` in `session.start` and `$.session.cwd()` give the folder the session runs in. `$.session.root()` gives where the session started or where `/cd` moved it. `$.session.repo().root` gives the git repository root. A session started in `docs/ideas` gave that subfolder for `cwd` and `root`, and the repository root for `repo.root`. `$.process.run` and `$.fs` resolve a relative path against the session's folder. For a git worktree, the type file says `repo.root` is the main working tree, which is not the worktree's workspace. The safe path is the one tested: run `brain status --json` in the session's folder and let Brain find its root through git, which worked from the subfolder.

For IDEA-015#12: the views can open through commands that the same mod registers, in the same `session.start` that opens IDEA-013's question. How the user opens them stays Peter's decision.

Still unknown, none of which changes the architecture: whether `bun` is on `PATH` when the Desktop app or the VS Code extension starts Claude Code (Brain's classic hook has the same need); what happens when a mod command has the same name as another plugin's command (the type file says registering a name again replaces it); and the `$.session.repo()` worktree case, which no run tested.
