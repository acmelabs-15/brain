### Short answer

- An idea stores its status. A spec stores none. An effort is not a record: its state is worked out each time from an idea's `status:` and from a plan's rows (A02, B01, D01).
- Three writers set an idea's stored status today. The CLI writes `define` from a template. The spec skill's fill step writes `specced`, and the planner reaches the same step for a spec that came in the chat. Interview-me's Finish writes `specced` too, and `done` with `result:`. No instruction names who writes `parked`. Real records store it all the same: 12 ideas in two repos were created as `parked`, and 8 of them went back to `define` later (A01, A09 to A13, A23, B16).
- No line is written to take an idea out of `specced`, `done` or `parked`. The spec skill's `specced` line names no condition on the idea's current status, so it can do that as a side effect (A14).
- By the spec skill's step order, the idea becomes `specced` when `spec.md` is filled, before the user reviews and approves the spec (A10). The one real case that was found does not match that text: a spec names an idea, the user rejected the spec draft, and the idea stores `define` (A22).
- No instruction and no code writes a state of a spec at any moment. Created, written, approved, planned, built, reviewed, shipped, parked and superseded leave no stored mark on the spec. Two of these states can be worked out from the plan rows: "a row is still to do" and "no row is still to do" (B01 to B14).
- A spec has two more forms than the one that `brain new-doc SPEC` and the spec skill make. The planner creates the spec folder and fills `spec.md` for a spec that came in the chat. A spec can stay in another spec tool, with no file of Brain at all (B16, B17).
- Instructions rely on "approved" as a state: the router, the workspace document, the commit contract and one vendored skill. No file or field records the approval of a spec, and a plan row has no approved value (E10).
- The code knows one flag per effort, `finished`, and three stage words: `define`, `build`, `finished`. An idea is finished unless its status is exactly `define`. A spec is finished unless a plan row is `open` or `in-progress` (D01 to D04).
- Two gaps hide real work. A spec with no plan row counts as finished, so the effort drops out of the report between "specced" and the first plan row, unless the git branch names it and no other effort; then it reads `finished`. A plan whose last row is closed also counts as finished, so nothing marks the spec as a whole as built, verified, reviewed or shipped. Each closed task row holds its commit and its verification outcome, and by instruction a task is reviewed before its row closes. Recorded evidence says that this review has no clear owner (C07, C12, D06, D07, D08, probes P5, P9 and P14).
- `brain check` ties a stored idea status to the idea's own content in one rule on the body, only for `specced` and `done`, and in one schema rule: `done` needs `result`. It does not look for the spec of a specced idea. No rule ties `define` or `parked` to the rows, the fog or the confirmation (A15, A16, A19).
- Three kinds of reader rely on these values: the code (`effort.ts`, `status.ts`, `plan.ts`, `check.ts`, the session-start hook), the instructions that choose an owner or a next step (the workspace document, the router, interview-me's Resume, the build, plan, review and test texts), and the views of IDEA-015, which are decided and not built in this worktree (section 4).
- The stored value and the real state drift in this repo today. Nine specs read as finished, and their own prose `Status:` lines say "draft for review" in four of them. IDEA-004 is `parked` and means "split and emptied". A stored spec state existed before in two forms, a spec index kept by hand and the prose `Status:` lines, and the two disagreed with each other. When the index was deleted, the prose line was stale for four specs and the index for one (section 7, I04).
- Under DEC-051, a stored spec status has no writer, no reader, no template line and no schema field today. For a migrated spec no field holds a first value. The old bodies and other records hold marks that were made by hand: the prose `Status:` line, the ticks, approval lines and "built" notes in plans, the capability map record, the history note, and the deleted spec index in git. Each can be stale (B20, F07, H04, I04, I06). Three of DEC-051's five values (open, in-progress, superseded) are findings on an idea today (A19). Section 8 lists each place as a fact. It gives no design.
- An earlier draft answered the same question and was not adopted. DEC-018 of 2026-11-05 put a spec's status in frontmatter and let that one field hold approval, the result of review and ship, and "built". It is a held draft in another worktree of this repo, and nothing builds on it (I10, I11).
- The recheck added five facts on the lifecycle. An idea of a request with several capabilities is `specced` at its first module spec (B18). An idea that idea-refine saved fails the finished-idea rule on its fog (A21). No instruction sets a plan row back to `open` (C09). A migrated plan held live ticks after its migration (H11). IDEA-002 and IDEA-003 ended as files left in other worktrees, with `status: define` (H09).
- The second repair added these facts. In real records `parked` stands for three states: set aside, split off and not picked yet, and split and emptied (A23). Two Resume rules name the drift between a stored row status and the real state, and give the repair (E11). A handoff document and a progress file hold state outside the workspace, and a handoff outranks the report (C14, E12). A plan row's `superseded by NN` has no instructed writer, and a replan is the one instructed way from a finished spec back to build (C10). A removed map row ends with no status value (C13). The Definition of Done is a second gate before "done", and it uses the word at three levels (C11). One migrated record got a status later, by hand (F08). The views prototype reads an idea with no status as `define`, where `effort.ts` reads it as finished (I12). The stage Define ends later than the status `define` (D13). `brain check` compares neither a spec's `sources:` with the idea's status nor an idea's `result:` with the decision's status (A24).

### 3. An effort, its stage and its selection

An effort is "the idea or spec that a session works on". It has no file and no field of its own (D01).

How the state of an effort is worked out:

| Step | Rule | Finding |
|---|---|---|
| The flag `finished`, for an idea | True unless the frontmatter parses and `status` is exactly `define`. So `specced`, `done`, `parked`, any other value, a missing status and frontmatter that cannot be read all give `finished` | D02 |
| The flag `finished`, for a spec | True unless `tasks/plan.md` has a row that is `open` or `in-progress`. No plan file, no plan table, no row, and a migrated plan (its old body holds no such table) all give `finished`. No frontmatter of the spec is read | D02 |
| The stage | `define` for an idea, `build` for a spec, `finished` when the flag is true | D03 |

### 5. Changes that no instruction or code covers today

1. **Every state of a spec.** Created, written, approved, planned, started, built, reviewed, shipped, set aside and replaced have no stored mark on the spec (B01, B06, B09, B11).
2. **`parked` on an idea.** The value has a meaning and no instructed writer, no step and no check. Real commits write it at an idea's creation, for an idea that is split off and not picked yet, and they change it back to `define` (A13, A16, A23).
3. **The way back.** No instruction says what a parked idea's status becomes when the user resumes it, and none takes an idea out of `specced` or `done`. In a second repo, eight ideas went from `parked` to `define` in one commit, and the idea files give no reason (A14, A23).
4. **An idea that is replaced, split or merged.** No value and no instruction exists (A13, H02).
5. **"Defined" as its own state.** Between the last resolved row and the status change, the idea reads `define` with no next step. Nothing shows that it waits for Finish (probe P3).
6. **The gap between `specced` and the first plan row.** The idea is finished, and the new spec is finished too, so the effort is in no report. RES-069 names this as finding K3, and IDEA-008#01 is an open row on it. A branch does not help when the idea and the spec share a slug: it then selects neither. Until 0.13.0 the hand-written status note was the only place for a next step such as "run /plan"; DEC-014 removed the note and gave this state no new place (D04, D06, H07, I05).

Nothing marks the spec as a whole as built, verified, reviewed or shipped, and nothing in the workspace marks a review verdict or a ship decision. Per task, the closed row holds the commit and the verification outcome, and it stands for "reviewed" by instruction only; recorded evidence says that the review has no clear owner. The idea stays `specced`. Until 0.13.0, work after the last row, "such as a merge or a release", reached the report only through the status note. Where they overlap or disagree:

- **`define` is a stage word and a stored idea status.** The code compares the stored word to set the flag, then prints the same word as the stage. DEC-051 calls `define` "a stage name rather than a status" (D02, D03, J01).
- **`finished` is a stage word that the glossary does not list.** It stands for four stored idea values or states (`specced`, `done`, `parked`, unknown) and for three spec states (never planned, all rows closed, migrated) (D02, D03).
- **`build` is shown for a spec that is only planned.** A plan with rows that are all `open` gives `Stage: build`. The glossary's "plan" stage has no worked-out form, and the moment between spec and plan has no stage at all (D03, D06, probe P7).
- **Verify, review and ship exist only in instructions.** Six stages are named in the glossary, the protocol, the router, the stage-boundaries reference and one test constant, among other texts. Two vendored texts name them too, and one of those puts BUILD, VERIFY, REVIEW and SHIP under the column head "Phase". The code works out three words, and nothing in the workspace marks the last three stages (D03, D10).
- **"The active effort is the one that is not finished."** The code returns a finished effort when the git branch names it and no other effort, and it reports several efforts when several are not finished (D04, D07, probe P14).
- **A migrated file is read in two ways.** `effort.ts` reads its status and its rows like those of any file. `status.ts` reads none of its rows. `brain check` skips its rows and the finished-idea rule (D12, F03).
- **Two stored status vocabularies stay outside DEC-051.** A decision record's status and a research record's status and outcome decide whether a map row can be `resolved`. DEC-051 names "ideas, specs and the rows of ideas and specs" only, and IDEA-016's Evidence says the two "are not part of this alignment unless Peter says so" (J02).
- **"Superseded" names its target today, and DEC-051 lists the bare word.** A row stores `superseded by NN` and a decision stores `superseded by DEC-NNN` (J02). The form already drops targets: four rows of IDEA-016 were each replaced by two or three rows, and each cell names one of them. For a spec the target can be a record of another kind: SPEC-005 was replaced by a decision record, which was replaced in turn (F08, J03).
- **"Finished" has two wordings.** The workspace document says a `specced` or `done` idea is finished, "and a `parked` idea waits until the user names it". The code has one flag for all three. Four fixture copies of the workspace document say "An idea with `status: specced` is done", which uses the stored word `done` for another status (D09, D11).
- **The spec skill has its own stage names.** SPECIFY, PLAN, TASKS and IMPLEMENT, "Stage 0" to "Stage 4". The router maps them onto define, plan and build (D10).
- **Two worked-out models of a spec's state exist.** `brain status` gives build or finished. DEC-035 gives five states for the views from the same rows, and DEC-036 adds Migrated. "Not planned" in DEC-035 is "finished" in `effort.ts` (D02, I03).
- **`/build auto` needs an active spec, and then plans a spec that has no row.** Its step 1 stops when "no spec is active". Its step 3 starts planning when the plan "holds no task row yet". By the row rule, a spec with no row is finished. So these steps reach such a spec only when the user or the branch names it (B13, D02, D09).
- **"Stage from current rows."** The workspace document's table says the Stage line gives each effort's "stage from current rows". For an idea the code reads the stored `status`, not the rows: an idea in `define` whose rows are all resolved stays `define` (E02, D02, probe P3).
- **A stored "ready for review" against DEC-051.** The held draft DEC-018 moved a spec's stored status to "ready for review" when the last task row resolves. DEC-051 keeps ready and in review worked out and never stored. DEC-018 is not adopted, so this is an earlier view, not a conflict between two decisions (I10, J01).
- **"A migrated idea's status remains open for review."** The migration writes no status. `open` is not an idea status today, and DEC-051 makes `open` a shared value, so the sentence can be read in two ways (A05, J01).
- **The row word `resolved` and the idea word `done` name one concept**, as DEC-051 says. The code already treats them alike: a resolved row "is done" in the comment of `graph.ts`, and a finished idea must have no row still to do (A15, C04, J01).
- **The stage Define ends later than the status `define`.** By the router, Define holds "confirmed intent in an idea and its DEC/RES records, then a spec when needed", and the spec skill's Stages 0 and 1 "cover define". So the writing, the review and the approval of a spec are inside the stage. The idea's `define` ends, by the spec skill's line, when `spec.md` is filled. In the real case of a rejected spec draft, the idea stayed `define` (A22, D13).
- **`parked` holds three states in real records.** The glossary gives it one meaning: the user sets the idea aside. In two repos, 12 ideas were stored as `parked` at their creation, after a split and before any work on them; 8 of them went to `define` later. IDEA-004 is `parked` and means "split and emptied". DEC-051 has the values `open` and `superseded` beside `parked` (A23, H02, J01).
- **A map row has a fifth end, with no value.** A row beyond the destination is removed and recorded under Out of scope. Finish counts map rows only, so a removed row does not count (C13).
- **"Done" has three levels in one vendored reference.** The Definition of Done gives a level per task, per feature and per release, with a human approval "before merge or deploy". DEC-051 makes `done` the stored word for a row and for a spec (C11, J01).
- **Two code paths read an idea with no status in two ways.** `effort.ts` reads it as finished. The views prototype reads it as `define` (D02, I12).

Ways to drift that the rules allow today:

- A stored idea status with nothing behind it: `specced` with no spec (P6), `define` with all work done (P3, P13), `parked` with open rows (P12, R7).
- A `result` under a status that is not `done`: `status: define` with `result: DEC-001` passes the check (A19).
- Two instruction lines for one value: the spec skill and interview-me both set `specced`, on the same condition (a spec's `sources:` names the idea). - A stored copy of a worked-out value: the Parallel waves section. `brain check` reports it when it is stale, and two build dry checks rewrite it at each played close (C05, G08).
- A row status that trails its record: a row stays `in-progress` after its record is resolved, until the main session reads the result, and the same pair of values stands for two different waits (R8, R9). At this record's first check a row also stayed `open` while its research ran (R13).

- A wait between efforts that is prose only: the report shows the waiting effort with a next step (R14).
- A status that two modules would read in two ways: a migrated file that gets a status or a row table (D12).
- A spec that names an idea which is still `define`: no check compares `sources:` with the idea's status (P17, R19). It is the reverse of P6.
- A `done` idea whose `result:` names a decision that is `proposed`: the check looks only for the file (P18).
- State in a handoff document or a progress file, outside the workspace. By instruction a handoff outranks the report (C14, E12, R25).
- One stored word for several states: `parked` (R6, R7, R20).
- A `superseded by NN` that names one of several replacements (R23).

Two instructions name the drift between a row's status and the real state, and give the repair. A session that resumes a spec reconciles completed work with the real changes and the verification evidence before a task repeats. A session that resumes an idea reconciles its `open` and `in-progress` rows with the records by `from` (E11). So the instructions expect that a stored row status can trail the work, and Resume is the place that repairs it.

Contrary evidence to "drift": `brain check` reports no finding in this repo's 111 workspace files. By Brain's own rules, R1 to R10 are not errors (H08).
