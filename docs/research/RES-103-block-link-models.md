# RES-103: How work trackers store and name a block between two items

## Question
How do tools that track work store and name a block between two items: on one end, on both ends or as one link; what do "blocks" and "is blocked by" mean in each; and how do they model a gate that several items feed?

## Answer
Sufficient answer: for each tool below, with a source per claim, checked today:

- (a) where a block between two items is stored: one link object, a field on one item, or a field on each item;
- (b) the words for each direction and what each word means; whether the user can enter the block from either end, and what the other end then shows;
- (c) whether the reverse direction is stored or worked out, and what keeps the two ends in step when both are stored;
- (d) what ends a block: which status of the blocking item, and whether the tool enforces it or only shows it;
- (e) how the tool models a gate that several items feed and that later items wait on;
- (f) loops and missing targets: what the tool does with them.

Tools: Jira, Linear, GitHub Issues, Azure Boards, Taskwarrior, Beads, Org mode with org-edna, and Backlog.md or one more markdown task tool. Then one section on reported problems when one block is stored on both ends, with contrary evidence. The research gives facts only. It serves IDEA-016#34, IDEA-016#35 and IDEA-016#10.

### Summary
1. Each of the eight tools stores one block one time, where the storage is public. None stores two fields that a person keeps in step.
2. Database tools use one link with two end names: Jira, Linear, Azure Boards. The storage of Jira Cloud, Linear, GitHub and Azure is not public.
3. File tools use one field on the item that waits: Taskwarrior `depends`, Beads `depends_on_id`, Org `BLOCKER`, Backlog.md `dependencies`.
4. All tools except Org show both directions. The reverse direction is worked out from the one stored form.
5. Entry from either end: Jira, Linear, GitHub, Azure Boards, Beads. The tool changes the entry to the one stored form. Entry from one end only: Taskwarrior, Org, Backlog.md.
6. "A blocks B" and "B is blocked by A" mean the same in every tool that uses the words: B waits for A. Azure Boards says "Predecessor" and "Successor".
7. The direction words cause errors. Two Atlassian pages name "inward" and "outward" in opposite ways. Beads has open reports of a block read backwards.
8. A block ends when the blocking item is done or closed. Only Org refuses a status change. Beads and Backlog.md keep the item off the ready list. The other tools only show the block.
9. No tool has a checkpoint item whose only job is to join several blocks. A gate is an ordinary item with several blocks, or a parent item.
10. A milestone is a group with no block in GitHub, Linear and Backlog.md. A Beads `gate` waits on a condition outside the tool, such as a merged pull request.
11. Loops: Azure Boards, Taskwarrior, Beads and Backlog.md refuse them at entry. Jira permits them.
12. Contrary evidence: Debbugs and adr-tools store both ends in two files on purpose. One command writes both. Debbugs has reports of half-done writes.
13. GitLab stored one block in two forms, then moved all rows to one form.

### What the evidence supports
- **Which end stores a block (IDEA-016#35).** The file tools among the eight all store the block on the item that waits. None of them stores "blocks" on the blocking item. Taskwarrior closed the request for a `blocks` entry as "won't fix", because one command would then change many tasks.
- **What keeps two ends in step.** Where both ends exist, a tool writes both in one command: Debbugs, adr-tools, Notion. No tool in this research leaves two ends to a person. Debbugs shows the failure form: one command stopped part way through its writes.
- **Entry and storage are separate.** Jira, GitHub, Beads, GitLab and Obsidian Tasks accept both words at entry and write one form. GitHub's command-line tool sends `--add-blocking` as "blocked by" with the two issues swapped.
- **One form of "blocked by" (IDEA-016#10).** Each tool has one stored form per kind of item. Linear has two kinds, issues and projects, and each kind has its own relation object. GitLab is the only tool found with two stored forms for one kind, and it removed one.
- **A checkpoint outside a plan (IDEA-016#34).** The nearest forms are the Beads `gate` issue and a parent item. The Beads gate is a normal issue in the same graph, joined by normal blocks. Jira Plans documents one item with several blocks as the way to join. Linear and GitHub permit many blocks on one item.
- **Meaning of "blocked".** In Org, a blocked entry cannot be marked DONE. In the other tools, a blocked item should not start. Azure Boards and Jira Plans test dates, not the status of the blocking item.

### Limits
- Not established: the storage of Jira Cloud, Linear, GitHub and Azure DevOps Services. The record gives what each API shows.
- Not established: loops and missing targets in GitHub, Linear and Org; missing targets in Jira and Azure Boards. The docs do not say, and this research ran no test on a live account.
- UNVERIFIED: that a Jira release or a Jira epic never blocks an issue by itself. This research found no Atlassian page that says it does, and did not search for one in depth.
- The Debbugs and GitLab sources date from 2018 to 2020. They report past problems; they do not describe the current state of those tools.
- Method: the skill `brain:source-driven-development` was loaded. The web search tool and the page reader both answered. The command `brain sdd-cache` does not exist in Brain 0.13.0, so no cache validator is recorded.

## Findings

### Jira
- A Jira link type has three parts: a name, an outward description and an inward description. The default type is named "Blocks", with outward "blocks" and inward "is blocked by". Source: https://developer.atlassian.com/cloud/jira/platform/issue-linking-model/#issue-link-types, checked 2026-11-21.
- Atlassian defines the outward description as "how a work item affects other work items" and the inward description as "how a work item is affected by other work items". Source: https://support.atlassian.com/jira-cloud-administration/docs/configure-issue-linking/ (page dated 2025-09-25), checked 2026-11-21.
- Jira Data Center stores a link as one row of the table `issuelink`, with the columns `ID`, `LINKTYPE`, `SOURCE`, `DESTINATION` and `SEQUENCE`. The docs say the table "simply links the IDs of two issues together and records the link type". The words for both directions are columns `INWARD` and `OUTWARD` of the one row of `issuelinktype`. Source: https://developer.atlassian.com/server/jira/platform/database-issue-fields/#issue-links, checked 2026-11-21.
- The Jira Cloud REST API has one link resource. `POST /rest/api/3/issueLink` takes one body with `type`, `inwardIssue` and `outwardIssue`. `GET /rest/api/3/issueLink/{linkId}` returns one object with one `id` and both issues. `DELETE /rest/api/3/issueLink/{linkId}` removes it. Source: https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issue-links/, checked 2026-11-21.
- On one issue, the API field `issueLinks` lists each link with the full type and either `inwardIssue` or `outwardIssue`. The docs say "if the issue link data contains an `inwardIssue` field, the link should be labeled with the value of the `type.inward` field". Jira thus works out the label of each end from one link when it shows the issue. Source: https://developer.atlassian.com/cloud/jira/platform/issue-linking-model/#issue-link-directionality, checked 2026-11-21.
- The same page says "Jira issue links are bidirectional, however, the semantics of each direction is only interpretable at the user interface level and not at the API level", and that the links "are drawn with labeled ends rather than arrows implying direction". Source: https://developer.atlassian.com/cloud/jira/platform/issue-linking-model/#issue-link-directionality, checked 2026-11-21.
- The user picks a link type by its label and can add the link from either issue: the picker lists "is blocked by" and "blocks" as two entries. Source: https://support.atlassian.com/jira-software-cloud/docs/link-issues/, checked 2026-11-21.
- Two Atlassian pages name the ends in opposite ways. The Data Center admin page lists the default type as "blocks / is blocked by", then says: "Issue A that is blocked by Issue B has an outward link of type is blocked by". The developer page gives outward as "blocks". Source: https://confluence.atlassian.com/spaces/ADMINJIRASERVER/pages/938847862/Configuring+issue+linking and https://developer.atlassian.com/cloud/jira/platform/issue-linking-model/, checked 2026-11-21.
- JQL searches the name and both descriptions of a link type together. For the default "Blocks" type, the name equals the outward description, so a search cannot isolate the outward end unless an admin renames the type. Source: https://support.atlassian.com/jira-cloud-administration/docs/configure-issue-linking/, checked 2026-11-21.
- Jira Cloud does not enforce a block. An open Atlassian suggestion states: "there is no out-of-the-box condition that evaluates the status of linked issues (such as those with an 'is blocked by' link) in order to allow or prevent a transition. As a result, dependency rules are typically enforced through conventions, automation, or third-party apps". Source: https://jira.atlassian.com/browse/JRACLOUD-97982 (created 2026-03-31, unresolved), checked 2026-11-21. An older suggestion with 518 votes asks for the same and is unresolved. Source: https://jira.atlassian.com/browse/JRACLOUD-43369, checked 2026-11-21.
- In a Jira plan, a dependency is an issue link. "Incoming dependency ('is blocked by') means the issue is dependent on the previous issue being completed". "Outgoing dependency ('blocks') means the issue blocks the next issue being started". The two badges "are referring to the same dependent relationship, only from different perspectives". The badges turn red when dates conflict. Source: https://confluence.atlassian.com/jirasoftware/dependencies-in-advanced-roadmaps-1688898866.html (last modified 2025-12-03), checked 2026-11-21.
- An admin chooses which link types count as plan dependencies and can "Swap" the order of a type. The default is "If A blocks B then A is scheduled before B". Source: https://confluence.atlassian.com/jiraportfolioserver/configuring-issue-dependencies-802170496.html and https://support.atlassian.com/jira-software-cloud/docs/configure-dependencies-in-jira-for-advanced-roadmaps/, checked 2026-11-21.
- One item can have many incoming dependencies: "Work item C can't start until work item A and work item B are complete. Work item C can have an incoming dependency from both". This is the documented Jira form of a gate: one issue with several "is blocked by" links. Source: https://community.atlassian.com/learning/course/jira-plans-tutorial/lesson/jira-plans-dependencies, checked 2026-11-21.
- Jira does not stop a loop of ordinary links. Atlassian calls them "soft links" that "wouldn't cause any malfunction", unless an app or Advanced Roadmaps walks the links: then a "cyclic link or loop may cause malfunctions", shown by a `StackOverflowError` or `OutOfMemoryError`. Atlassian gives a database query to find the loops. Source: https://support.atlassian.com/jira/kb/how-to-identify-cyclic-issue-links-or-loops-in-jira/ (Data Center only), checked 2026-11-21.

### Linear
- The user marks an issue as blocked by another with `M` then `B`, or as blocking another with `M` then `X`. The blocked issue shows the other issue "with an orange flag under Blocked by". The blocking issue shows it "with a red flag under Blocks". Source: https://linear.app/docs/issue-property#issue-relations (the older address https://linear.app/docs/issue-relations now leads to the properties home page), checked 2026-11-21.
- "Once the blocking issue has been resolved, the relationship moves under Related." The docs name no rule that stops work on a blocked issue. Source: https://linear.app/docs/issue-property#issue-relations, checked 2026-11-21.
- The Linear API has one object per relation, `IssueRelation`, with `id`, `issue`, `relatedIssue` and `type`. The schema says: "A relationship between two issues, with issue as the source and relatedIssue as the target. For blocks, the source blocks the target". Source: https://github.com/linear/linear/blob/2ca00918e3ae699a0aa1a6b07330b433397cd201/packages/sdk/src/schema.graphql#L16493 (commit of 2026-11-18), checked 2026-11-21.
- The only block type is `blocks`. The enum `IssueRelationType` holds `blocks`, `duplicate`, `related` and `similar`. There is no "blocked by" type. Source: same file, line 16615, checked 2026-11-21.
- An issue reads its two directions through two fields over the same objects. `relations` holds "Relations whose source is this issue. For a blocks relation, this issue blocks relatedIssue". `inverseRelations` holds "Relations whose target is this issue. For a blocks relation, the source issue blocks this issue". Source: same file, lines 13806 and 13953, checked 2026-11-21.
- The create input requires that the two ends differ: `relatedIssueId` "Must differ from issueId". The schema states no check for a longer loop. Source: same file, line 16557, checked 2026-11-21.
- Linear has a second, separate block between projects. "Project dependencies provide a visual depiction of blocking relationships on timeline views. Currently we only support a end -> start dependency." The user picks "Blocked by..." or "Blocking..." and both projects then show "Blocked by" and "Blocking" fields. A blue line is a dependency "that has not been violated"; a red line is one "that has been violated". Source: https://linear.app/docs/project-dependencies, checked 2026-11-21.
- A project dependency is one `ProjectRelation` object with `project`, `relatedProject`, `anchorType` and `relatedAnchorType`. Each anchor is `start`, `end` or `milestone`, and the relation can point at one `projectMilestone` on either side. The type is "Currently always dependency". Source: https://github.com/linear/linear/blob/2ca00918e3ae699a0aa1a6b07330b433397cd201/packages/sdk/src/schema.graphql#L30417, checked 2026-11-21.
- A Linear project milestone is a stage inside one project that holds issues: "Project milestones represent different stages in a project's lifecycle. You can easily create milestones, add issues to milestones, and track the progress of each milestone". The docs do not say that a milestone blocks an issue. Source: https://linear.app/docs/project-milestones, checked 2026-11-21.

### GitHub Issues
- The words are "blocked by" and "blocking". "Mark as blocked by" means "your issue depends on another issue being completed". "Mark as blocking" means "your issue is preventing another issue from being completed". The user can enter the block from either issue. Source: https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/creating-issue-dependencies (source file commit 7a720df of 2026-06-17), checked 2026-11-21.
- The REST API writes a block from one end only. It has `POST` and `DELETE` on `/repos/{owner}/{repo}/issues/{issue_number}/dependencies/blocked_by`, with the body field `issue_id`: "The id of the issue that blocks the current issue". The path `/dependencies/blocking` has `GET` only. Source: https://docs.github.com/en/rest/issues/issue-dependencies (API version 2026-03-10), checked 2026-11-21.
- The GraphQL API has the same shape. The only mutations are `addBlockedBy` and `removeBlockedBy`, with the inputs `issueId` ("The ID of the issue to be blocked") and `blockingIssueId`. The issue fields `blockedBy` ("A list of issues that are blocking this issue") and `blocking` ("A list of issues that this issue is blocking") are read fields. Source: https://github.com/github/docs/blob/8c77c2caeeb1311c33020cfb43dd67616b905c11/src/graphql/data/fpt/schema.docs.graphql#L415 and lines 20521 and 20551, checked 2026-11-21.
- The GitHub command-line tool offers both ends and sends one form. Its source says: "AddBlockingIDs / RemoveBlockingIDs name issues that this issue blocks. They are applied via the addBlockedBy / removeBlockedBy mutations with the arguments swapped". Source: https://github.com/cli/cli/blob/trunk/api/queries_issue.go#L658 (read at trunk, 2026-11-21), checked 2026-11-21.
- The state of the blocking issue ends the block in the counts. `IssueDependenciesSummary.blockedBy` is the "Count of issues this issue is blocked by". `totalBlockedBy` is the "Total count of issues this issue is blocked by (open and closed)". Source: https://github.com/github/docs/blob/8c77c2caeeb1311c33020cfb43dd67616b905c11/src/graphql/data/fpt/schema.docs.graphql#L21922, checked 2026-11-21.
- GitHub shows a block; the docs name no rule that stops a blocked issue from closing. "Blocked issues are marked with a 'Blocked' icon on your project boards or repository's Issues page". The search filters are `is:blocked`, `is:blocking`, `blocked-by:` and `blocking:`. One issue takes "up to 50 issues for each relationship type". Source: https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/creating-issue-dependencies and https://github.blog/changelog/2025-08-21-dependencies-on-issues/, checked 2026-11-21.
- A GitHub milestone is a named group with a due date and a completion percentage. An issue has one `milestone` field. The docs name no block between a milestone and an issue. Source: https://docs.github.com/en/issues/using-labels-and-milestones-to-track-work/about-milestones, checked 2026-11-21.

### Azure Boards
- The link type is "Successor-Predecessor", reference name `System.LinkTypes.Dependency`, topology "Dependency". "Choose Predecessor when linking to a work item that should complete before the current item. Choose Successor when linking to a work item that should complete after the current item." Azure Boards does not use the words "blocks" or "blocked by" for this type. Source: https://learn.microsoft.com/en-us/azure/devops/boards/queries/link-type-reference?view=azure-devops, checked 2026-11-21.
- One link type has two names for its two ends. `ForwardName` is the "Name of the link at the source work item". `ReverseName` is the "Name of the link at the target work item. This name appears when a listing of the links at the target work item appears". Source: https://learn.microsoft.com/en-us/azure/devops/reference/xml/link-type-element-reference?view=azure-devops-2022, checked 2026-11-21.
- The API shows the two ends as a pair of relation types. `System.LinkTypes.Dependency-Forward` has the name "Successor" and `oppositeEndReferenceName` `System.LinkTypes.Dependency-Reverse`. The reverse has the name "Predecessor". Both carry `"acyclic": true` and `"directional": true`. Source: https://learn.microsoft.com/en-us/rest/api/azure/devops/wit/work-item-relation-types/list?view=azure-devops-rest-7.1, checked 2026-11-21.
- A client adds the link on one work item, from either end. It adds one entry to that item's `relations` list, with `rel` set to the forward or the reverse name and `url` set to the other item. Microsoft's own tool maps "successor" to `Dependency-Forward` and "predecessor" to `Dependency-Reverse` and sends one `add` on `/relations/-`. Source: https://github.com/microsoft/azure-devops-mcp/blob/main/src/tools/work-items.ts and https://learn.microsoft.com/en-us/rest/api/azure/devops/wit/workitembatchupdate?view=azure-devops-rest-7.0, checked 2026-11-21.
- The query language reads links as their own set: `FROM WorkItemLinks`, with `[Source]`, `[Target]` and `[System.Links.LinkType]`. Source: https://learn.microsoft.com/en-us/azure/devops/boards/queries/wiql-syntax?view=azure-devops, checked 2026-11-21.
- Azure Boards refuses a loop for this type. "An error appears when you attempt to create circular relationships." The Dependency topology is there "to restrict circular relationships", and "You can't create a dependent link between two work items that are linked to the same work items via dependent links". Source: https://learn.microsoft.com/en-us/azure/devops/boards/queries/link-type-reference?view=azure-devops and https://learn.microsoft.com/en-us/azure/devops/reference/xml/link-type-element-reference?view=azure-devops-2022, checked 2026-11-21.
- Azure Boards shows a dependency by dates; it does not stop work. Delivery Plans show a green icon for "No dependency scheduling issues" and a red icon for conflicts. "Dependency conflicts occur when a successor work item is scheduled to complete before its predecessor." The test uses the Target Date or the iteration end date, not the state of the predecessor. Source: https://learn.microsoft.com/en-us/azure/devops/boards/plans/track-dependencies?view=azure-devops, checked 2026-11-21.
- The Predecessor-Successor type can "Support one-to-many relationships". Source: https://learn.microsoft.com/en-us/azure/devops/boards/queries/link-type-reference?view=azure-devops, checked 2026-11-21.

### Taskwarrior
- The block lives in one attribute, `depends`, on the task that waits. "Declares this task to be dependent on id1 and id2. This means that the tasks id1 and id2 should be completed before this task. Consequently, this task will then show up on the 'blocked' report". Source: https://github.com/GothenburgBitFactory/taskwarrior/blob/783af9d3859c169908235c5041b8d57c62d0eaee/doc/man/task.1.in#L895 (develop, 2026-11-17), checked 2026-11-21.
- The reverse direction is worked out and never stored. The virtual tags are `BLOCKED` ("Is the task dependent on another incomplete task?") and `BLOCKING` ("Does another task depend on this incomplete task?"). Virtual tags "are evaluated at run time, which means they do not require direct metadata, and therefore do not occupy space in the database". Source: https://taskwarrior.org/docs/tags/, checked 2026-11-21.
- The code works out both flags in one pass over the `depends` lists. A pair counts only when neither task is `completed` or `deleted`. A `depends` entry whose target is not in the loaded set is skipped without an error. Source: https://github.com/GothenburgBitFactory/taskwarrior/blob/783af9d3859c169908235c5041b8d57c62d0eaee/src/TDB2.cpp#L541, checked 2026-11-21.
- Taskwarrior refuses loops and self-blocks when the user adds a dependency: "A task cannot be dependent on itself." and "Circular dependency detected and disallowed." A dependency on an unknown id fails with "Could not create a dependency on task {1} - not found". Source: https://github.com/GothenburgBitFactory/taskwarrior/blob/783af9d3859c169908235c5041b8d57c62d0eaee/src/Task.cpp#L973, checked 2026-11-21.
- Taskwarrior does not stop work on a blocked task. On start it prints "Task {1} is blocked by:" with the list, when `dependency.reminder` is on. A blocked task gets a lower urgency (`urgency.blocked.coefficient=-5.0`) and a blocking task a higher one (`urgency.blocking.coefficient=8.0`). Source: https://github.com/GothenburgBitFactory/taskwarrior/blob/783af9d3859c169908235c5041b8d57c62d0eaee/src/dependency.cpp#L150 and https://github.com/GothenburgBitFactory/taskwarrior/blob/783af9d3859c169908235c5041b8d57c62d0eaee/doc/man/taskrc.5.in#L1098, checked 2026-11-21.
- When a task in the middle of a chain is completed or deleted, Taskwarrior asks "Would you like the dependency chain fixed?" and then makes each blocked task depend on the tasks that the removed task waited on. Source: https://github.com/GothenburgBitFactory/taskwarrior/blob/783af9d3859c169908235c5041b8d57c62d0eaee/src/dependency.cpp#L107, checked 2026-11-21.
- Users asked for a stored or typed `blocks:` attribute and the core refused. The 2014 request was closed "won't fix": "contrary to the current model where only one task is modified per run, it needs to modify up to an infinite number of tasks that are being blocked". Source: https://github.com/GothenburgBitFactory/taskwarrior/issues/1439, checked 2026-11-21.
- In 2025 a maintainer said a `blocks` entry "would make sense in the UI if it could be translated into the same dependency mapping as the `depends` property", and that a change to another task by `task A modify` would be unusual. The add-ons that give `blocks:` all write `depends` on the other task. Source: https://github.com/GothenburgBitFactory/taskwarrior/discussions/3882 and https://github.com/mokrunka/taskwarrior-blocks-capsule, checked 2026-11-21.
- Taskwarrior has no gate object. A gate is an ordinary task whose `depends` lists several tasks; later tasks list that task in their own `depends`. This follows from the one attribute above; the docs name no milestone type. Source: https://github.com/GothenburgBitFactory/taskwarrior/blob/783af9d3859c169908235c5041b8d57c62d0eaee/doc/man/task.1.in#L895, checked 2026-11-21.

### Beads
- The repository `steveyegge/beads` now lives at `gastownhall/beads`. All Beads sources below are at commit 78624109 of 2026-11-20. Source: https://github.com/gastownhall/beads, checked 2026-11-21.
- A block is one dependency record with `issue_id`, `depends_on_id` and `type`. For the type `blocks`, `issue_id` is the issue that waits. Source: https://github.com/gastownhall/beads/blob/78624109904655d7a4609f27d34eb0982cd8963f/internal/types/types.go#L1216 and https://github.com/gastownhall/beads/issues/7090, checked 2026-11-21.
- The user can enter the block from either end and Beads stores one form. `bd dep add issue-2 issue-1` means "issue-2 depends on issue-1 (issue-1 blocks issue-2)". `bd dep issue-1 --blocks issue-2`, `--blocked-by` and `--depends-on` give the same record. In a batch file, "`blocks:id`: id depends on the new issue". Source: https://github.com/gastownhall/beads/blob/78624109904655d7a4609f27d34eb0982cd8963f/docs/core-concepts/dependencies.md, checked 2026-11-21.
- The reverse direction is worked out. `bd dep tree issue-id --direction=up` and `bd dep list issue-id --direction=up` answer "What depends on this issue?". The JSON output carries `dependency_count` and `dependent_count`. Source: same file and https://github.com/gastownhall/beads/blob/78624109904655d7a4609f27d34eb0982cd8963f/docs/reference/json-schema.md, checked 2026-11-21.
- The closed status of the blocking issue ends the block. "When issue-1 is open, issue-2 won't appear in `bd ready`. Once issue-1 is closed, issue-2 unblocks automatically." "An issue is ready when ALL of its blocking dependencies are closed." Beads applies this to the ready list; the docs name no rule that stops a status change on a blocked issue. Source: https://github.com/gastownhall/beads/blob/78624109904655d7a4609f27d34eb0982cd8963f/docs/core-concepts/dependencies.md, checked 2026-11-21.
- Only four dependency types block: `blocks`, `parent-child`, `conditional-blocks` and `waits-for`. Six more types, such as `related` and `discovered-from`, are "graph annotations only". Source: same file, checked 2026-11-21.
- A Beads gate is an issue of type `gate`. "A gate is a bead like any other: created open, it blocks its waiters through a normal dependency edge, and the step becomes ready the moment the gate closes." Gate types are `human`, `timer`, `gh:run`, `gh:pr` and `bead`. A gate waits on a condition outside the graph; it is not a join of several issues. Source: https://github.com/gastownhall/beads/blob/78624109904655d7a4609f27d34eb0982cd8963f/docs/workflows/gates.md, checked 2026-11-21.
- Beads has one more form for a join: the `waits-for` type, where "B waits for all of A's children", with the mode `all-children` or `any-children` in the edge metadata. An epic is the parent in the documented example. Source: https://github.com/gastownhall/beads/blob/78624109904655d7a4609f27d34eb0982cd8963f/docs/core-concepts/dependencies.md and https://github.com/gastownhall/beads/blob/78624109904655d7a4609f27d34eb0982cd8963f/internal/types/types.go#L1578, checked 2026-11-21.
- Beads refuses loops at write time and can list them: "`bd dep add` checks for cycles before committing", and `bd dep cycles` finds stored ones. Source: https://github.com/gastownhall/beads/blob/78624109904655d7a4609f27d34eb0982cd8963f/docs/core-concepts/dependencies.md, checked 2026-11-21.
- A missing target in the same database is an "orphaned dependency": `bd doctor` reports it and `bd doctor --fix` removes it. A target in another project is stored with a warning and "an unconfigured or unavailable project remains blocking". Source: same file, checked 2026-11-21.
- Beads has open reports that the direction of a block is read backwards. The stored type word is `blocks`, but the record reads from the blocked issue: "for `blocks` the stored `IssueID` is the blocked issue, so it comes out reversed" in the history text. Source: https://github.com/gastownhall/beads/issues/7090 (open, 2026-10-02), checked 2026-11-21.
- `bd dep list` "never says which end of the edge that neighbour sits on", so "a reader taking the obvious reading gets the graph backwards". Source: https://github.com/gastownhall/beads/issues/5960 (open, 2026-08-22), checked 2026-11-21.
- An earlier bug stored `--deps blocks:X` in the wrong direction; the fix "swaps IssueID/DependsOnID when `blocks:` is explicitly specified". Source: https://github.com/gastownhall/beads/pull/1742 (closed, 2026-02-14), checked 2026-11-21.

### Org mode and org-edna
- Built-in Org blocks by position in the file, with nothing stored per block. With `org-enforce-todo-dependencies`, "Org blocks entries from changing state to DONE while they have TODO children that are not DONE". With the property `ORDERED` on a parent, "each of its TODO children is blocked until all earlier siblings are marked as done". Source: https://orgmode.org/manual/TODO-dependencies.html, checked 2026-11-21.
- Org enforces this block: the state change to DONE is refused. The user can override it with `C-u C-u C-u C-c C-t`, or with the property `NOBLOCKING`. Blocked entries can be dimmed in the agenda. Source: https://orgmode.org/manual/TODO-dependencies.html, checked 2026-11-21.
- A parent entry is the built-in Org gate: it cannot become DONE until all its children are DONE. Source: https://orgmode.org/manual/TODO-dependencies.html, checked 2026-11-21.
- `org-depend.el` stores a block in one property, `BLOCKER`, on the entry that waits. Its words are "treated as entry IDs", and "If any of these entries is not yet marked DONE, the current state change will be blocked". Source: https://orgmode.org/worg/org-contrib/org-depend.html, checked 2026-11-21.
- `TRIGGER` is not the reverse of `BLOCKER`. It sits on the other entry and holds an action: it switches a named entry to a keyword when this entry becomes DONE. The tool does not keep `BLOCKER` and `TRIGGER` in step. Source: https://orgmode.org/worg/org-contrib/org-depend.html, checked 2026-11-21.
- org-edna uses the same two properties. "A blocker indicates conditions which must be met in order for a heading to be marked as DONE. Typically, this will be a list of headings that must be marked as DONE." "A trigger is an action to take when a heading is set to done". Source: https://www.nongnu.org/org-edna-el/, checked 2026-11-21.
- org-edna can count the targets. "A blocker says 'If ANY heading in TARGETS meets CONDITION, block this task'". `consider(all)`, `consider(FRACTION)` and `consider(NUMBER)` change that rule. The default condition is `!done?`, "block if any target heading isn't done". Source: https://www.nongnu.org/org-edna-el/, checked 2026-11-21.
- In Org, "blocked" means that the entry cannot be marked DONE. It does not mean that the entry cannot start. Source: https://orgmode.org/manual/TODO-dependencies.html and https://www.nongnu.org/org-edna-el/, checked 2026-11-21.

### Backlog.md
- Backlog.md keeps each task as a markdown file. A block is one list, `dependencies`, on the task that waits: "`dependencies` contains the stored direct dependency IDs". All sources below are at commit 9087714 of 2026-11-21. Source: https://github.com/MrLesk/Backlog.md/blob/9087714336b3de5641a0ec5ed5d1342d12d68205/CLI-INSTRUCTIONS.md, checked 2026-11-21.
- The reverse direction is worked out and never stored. The `dependencyGraph` is "derived from the whole visible corpus at read time and never stored in the Markdown file". "'Dependents' means the tasks this one blocks. It is the reverse of the task's own dependency list, and nothing on it is editable from here; change it on the task that declares it". Source: same file, section "Dependency graph in task detail", checked 2026-11-21.
- The user enters a block from one end only: `backlog task edit 7 --dep task-1 --dep task-2`. Source: same file, section "Dependency Management", checked 2026-11-21.
- The final status of the blocking task ends the block. `isReady` is "derived from the whole visible corpus at read time and never stored: it is `true` when the task is unfinished and every dependency it names resolved to a completed task". It is shown and used as the filter `task list --ready`; the docs name no rule that stops work. Source: same file, checked 2026-11-21.
- Missing targets fail closed at read time. "`unknown task ID` means no visible task claims that ID... Neither is ever treated as satisfied". At write time the tool refuses: "The following dependencies do not exist". On delete, the tool "removes the dependencies and references other tasks and drafts hold to the deleted task". Source: same file and https://github.com/MrLesk/Backlog.md/blob/9087714336b3de5641a0ec5ed5d1342d12d68205/src/core/backlog.ts#L373, checked 2026-11-21.
- Backlog.md refuses loops at write time: "Task X cannot depend on itself" and "These dependencies would create a cycle: ...". A stored loop shows as `(cycle)` in the graph. Source: https://github.com/MrLesk/Backlog.md/blob/9087714336b3de5641a0ec5ed5d1342d12d68205/src/utils/task-builders.ts#L88 and CLI-INSTRUCTIONS.md, checked 2026-11-21.
- A Backlog.md milestone is its own file and a task names one milestone in a `milestone` field. The docs name no block between a milestone and a task. Source: https://github.com/MrLesk/Backlog.md/blob/9087714336b3de5641a0ec5ed5d1342d12d68205/CLI-INSTRUCTIONS.md, section "Milestone Management", checked 2026-11-21.

### Obsidian Tasks
- The Obsidian Tasks plugin stores a block on one end, inside the markdown line of the task that waits. The first task carries an `id` field; the second carries `dependsOn` with that id (in emoji form `🆔 abcdef` and `⛔ abcdef`). The meaning is "the second task cannot be started until the first task is completed". Source: https://publish.obsidian.md/tasks/Getting+Started/Task+Dependencies, checked 2026-11-21.
- The edit window offers both ends, "Before this" and "After this", and both write the same two fields. Ids are meant to be unique, "However, there is no checking for this". Source: same page, checked 2026-11-21.

### One block on both ends: reported problems and contrary evidence
- Debbugs, the Debian bug tracker, keeps each bug as status files and stores a block on both ends. Each bug has the fields `blocks` and `blocked-by`. Source: https://salsa.debian.org/debbugs-team/debbugs/-/blob/master/lib/Debbugs/Status.pm#L113 (read at master), checked 2026-11-21.
- One Debbugs command writes both ends in sequence: `set_blocks` first writes `blockedby` on the blocked bug, then opens each blocking bug and writes its `blocks` field. Source: https://salsa.debian.org/debbugs-team/debbugs/-/blob/master/lib/Debbugs/Control.pm#L313 (read at master), checked 2026-11-21.
- Debbugs has a reported half-done write: "While putting blocking into #885135, #885310 was archived, so all subsequent bugs were not properly blocked. This should either fail early, and block no bugs, or skip the archived bugs". The fix shipped as "Fix blocks/blockedby of archived bugs (Closes: #892060)". Source: https://www.mail-archive.com/debian-debbugs@lists.debian.org/msg03816.html (2018-03-04) and https://www.mail-archive.com/debian-debbugs@lists.debian.org/msg03826.html (changelog of debbugs 2.6.0), checked 2026-11-21.
- Debbugs has more reports from the same pair of fields. A merge failed because a `blockedby` entry named an archived bug: "Failed to forcibly merge 726171: can't find location for 726294". A merge failed because two bugs held the same `Blocked-By` set in a different order. A clone removed "all other blocks instead of adding them" (#820044). Source: https://www.mail-archive.com/debian-debbugs@lists.debian.org/msg03720.html, https://www.mail-archive.com/debian-debbugs@lists.debian.org/msg03802.html and https://www.mail-archive.com/debian-debbugs@lists.debian.org/msg03826.html, checked 2026-11-21.
- GitLab stored one block in two forms in one table: `TYPE_BLOCKS => 1` and `TYPE_IS_BLOCKED_BY => 2`. "The extra relation type adds complexity when querying for blocking/blocked issues". GitLab moved all rows of type 2 to type 1 and stopped saving type 2: "We will still be able to identify if an issue is `blocked` or `blocking` using the `target_id` and `source_id` keys." The move was done in production by 2020-11-16. Source: https://gitlab.com/gitlab-org/gitlab/-/work_items/225919, checked 2026-11-21.
- GitLab kept the word `is_blocked_by` at the entry point only. The API still takes `link_type` `blocks` or `is_blocked_by`: "`blocked_by` will be still accepted in our API otherwise it would be a breaking change". Source: https://gitlab.com/gitlab-org/gitlab/-/work_items/225919 and https://docs.gitlab.com/api/issue_links/, checked 2026-11-21.
- GitLab also stores a worked-out count, `blocking_issues_count`, on each issue, and reported "some inconsistencies with `blocking_issue_count` values" after the fill. Source: https://gitlab.com/gitlab-org/gitlab/-/work_items/237977, checked 2026-11-21.
- Bugzilla shows two fields, "depends on" and "blocks", and stores one row per block in the table `dependencies`, with the columns `blocked` and `dependson` and a unique index over both. It refuses loops: "This would create a circular dependency, which is not allowed." and "You can't make a bug block itself or depend on itself". Source: https://github.com/bugzilla/bugzilla/blob/35b7162b64c29171a6f8a9ae0955a6d8d96373fe/Bugzilla/DB/Schema.pm#L475 and https://github.com/bugzilla/bugzilla/blob/35b7162b64c29171a6f8a9ae0955a6d8d96373fe/template/en/default/global/user-error.html.tmpl#L448, checked 2026-11-21.
- adr-tools stores a link on both ends of two markdown files, on purpose. `adr link SOURCE LINK TARGET REVERSE-LINK` runs two writes in sequence, one per file: "LINK is the description of the link created in the SOURCE. REVERSE-LINK is the description of the link created in the TARGET". The tool has no command that checks the two ends against each other. Source: https://github.com/npryce/adr-tools/blob/b3279baf9be2207d1a4f4bbd608fd0b591c72aee/src/adr-link, checked 2026-11-21.
- Notion shows both ends as two properties and the system keeps them in step. For a relation of a database to itself, "Two-way relation" "creates two separate properties instead of one", and "Add pages to one property, and the other property updates on its own." The storage of Notion is not public. Source: https://www.notion.com/help/relations-and-rollups, checked 2026-11-21.
- The Breadcrumbs plugin for Obsidian reads typed links from markdown frontmatter and works out the reverse. "An implied relation is just the reverse of a real relation... Every real relation implies the opposite relation." A current fork states: "if A is `up` from B, then B is `down` from A". Source: https://breadcrumbs-wiki.onrender.com/docs/Getting%20Started/Relationships and https://github.com/michaelpporter/breadcrumbs, checked 2026-11-21.
- GitHub's own server for AI tools takes both words and writes one: "`blocking` is the inverse of `blocked_by` with subject/related swapped. Rejects a self-dependency before any API round-trip". Source: https://github.com/github/github-mcp-server/pull/2751 (merged 2026-06-26), checked 2026-11-21.
