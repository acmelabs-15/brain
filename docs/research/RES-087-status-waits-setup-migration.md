# RES-087: How setup and migration handle status and waits

## Question
How do setup and migration handle status and waits: the setup code, the layout-1 reader and migration, migrated files and the setup skill?

**In short.** Setup and the migration store no status and no wait for any item. A setup run writes two guidance files and moves an old status note to history. With the Codex adapter it also writes the protocol block, which holds rules on row status and user waits, into an `AGENTS.md`. The migration moves layout-1 files and adds a small frontmatter; it changes no byte of a body. Old state in a repo file stays in the body as text. Old state on an issue tracker is left behind by decision. No Brain code reads a checkbox, a prose Status line or a Dependencies line. After a migration, `brain status` reports "no active work" for work that the old files show as unfinished, when the branch names no effort.

### 2. How layout 1 is detected

Two code paths detect layout 1, and they use different rules. A third reader, `brain check`, has no layout-1 rule.

The two detectors disagree on four small trees (F21). A repo with only `CONTEXT.md` gets the layout-1 line from `brain status`, and setup treats it as a new install. A repo with only an old ADR, or only a DEC file with no frontmatter, gets five lines from `brain status`, and setup calls it layout 1. In those five lines the Red line still says "no docs/agents/workspace.md: run setup-brain; 1 brain check finding: run brain check"; only the layout-1 line and the word migrate are missing (F65). A repo with `tasks/plan.md` and a `workspace.md` that records no layout gets "no active work" from `brain status`, and setup calls it layout 1.

Two of the differences have a stated reason (F87). The glossary is left out of setup's list because "the glossary rename has its own question". `brain status` takes a present `workspace.md` as the mark of a migrated repo. No source says why the status list leaves out ADRs and records with no frontmatter. The protocol agrees with setup on the glossary: "a missing glossary alone needs neither" setup nor migration (F87).

An absent `workspace.md` is not a sign of layout 1 by itself. A repo of Brain 0.10.0 or 0.11.0 can hold layout-2 spec folders in `docs/specs` and no `workspace.md` (F82). Neither detector knows one old place: `tasks/done/<module>/plan.md` and `todo.md`. This repo held eight such folders. A hand-made commit moved seven, and one remains (F66, F67). The skill tells the agent to detect layout 1 from legacy specs, plans, intent docs, numbered ADRs and tracker guidance (F22).

Effects in Brain's readers, each stated with the row that owns its depth:

- The schema skips every field of need `new` when the marker is present, and it accepts only the value 0.8 for the marker (F35). Row 17 owns the schema.
- `brain check` skips the H1, the rows, the idea completion rule and the waves of a migrated file. A migrated decision with no `kind` gives one informational line (F36). Row 17 owns the checks.
- A migrated research record passes the schema with no `status`, but a resolved map row that names it gets a check finding: "is not answered research (status: undefined, outcome: absent)" (F73). So this repo's five migrated RES files cannot be the result of a map row as they are.
- `brain status` reads no rows from a migrated file. The effort finder counts a migrated idea and a migrated spec as finished (F37). Rows 18 and 19 own this code.
- On a copy of the migrated fixture, `brain status` prints "Stage: no active work" and "Next step: none". The migrated plan in that tree holds two unticked tasks, an unticked checkpoint and an open question (F37). When the branch names one migrated effort, the first line is "Stage: finished (...)" (F74).
- `brain plan` on a migrated plan exits 1 with "no table with the columns # | Task | Type | Status | Blocked by | Result". That is the result for this repo's SPEC-009 (F71).
- The marker is sticky in the readers. When a migrated plan later gains a layout-2 row table and keeps the marker, three readers differ: `brain plan` lays the waves, `brain status` shows "Stage: build" and "Next step: none", and `brain check` checks no row (F38, F71). When the marker goes, `brain check` applies every layout-2 rule to the old body (F38).
- A fourth code reader of the marker is the lifecycle check of Brain's own repo. It skips a migrated plan or todo in a spec folder, so the retired names in the old body give no finding (F72).
- This repo holds 33 files with the marker. 19 come from two runs of the migrate mode. 14 were marked by hand from `tasks/done/<module>/` (F39, F66). Rows 26 and 27 own the records.
- One of the 33, DEC-002, gained a `status` later and kept the marker. It got the status through the supersede rule of the DEC format (F39, F88).

No code and no instruction completes a migrated file to the full layout-2 form (F40). One instruction writes one field into a migrated record: the supersede rule (F88).
