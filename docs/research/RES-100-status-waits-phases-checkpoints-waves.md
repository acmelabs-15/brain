# RES-100: How phases, checkpoints and waves are handled everywhere

## Question
How are phases, checkpoints and waves handled everywhere: defined, stored, worked out, instructed, tested and shown?

## Answer
Sufficient answer: with a source per claim, end to end across code, instructions, tests, evals, docs and real records. The record states how each of the three is defined (glossary, planning skill, code comments) and where the definitions differ. It states what is stored (a checkpoint row) and what is only worked out (a phase, a wave). It states the code that derives them and its rules. It lists every instruction that creates, reads or acts on them. It states where they are shown (brain plan, a Parallel waves section, live against fixed waves). It states what tests and evals pin. It states whether any real plan in this repo uses them. It states what a phase's status and a phase's waits could be read from today, as facts for the decision on whether a phase becomes a record (IDEA-016 row 09). It names the contradictions between sources, what could not be established, and contrary evidence.

The record meets this condition after three steps of 2026-11-21: a repair from the first three check results, a second pass against the checked topic records of rows 17 to 27, and a second repair from the second round of the three checks. See "Checks" and "Second pass" below. Finding IDs (F01 to F145, with F54a, F60a, F60b, F85a and F86a) point to the Findings section.

### Short answer

- A checkpoint is stored. It is a plan row with the type `checkpoint`, with the same Status, Blocked by and Result cells as a task row, and one block of boxes in `tasks/todo.md` (F13, F14).
- A phase is not stored. Two functions work it out: the task rows that one checkpoint row names directly in its Blocked by cell. A phase has no name of its own, no number, no status and no wait of its own. The title of its checkpoint row is its only stored label, and the output names the phase by the number of that row (F15, F22, F27, F108).
- A wave is not stored as an item. `brain plan` works the waves out from the Blocked by cells of the rows that are `open` or `in-progress`. Each layout-2 plan that `brain plan` can put in order stores a text copy of that output in a "Parallel waves" section, and `brain check` reports the copy when it is missing or stale. A plan with one of four faults gets no wave: a row that breaks the format, a blocker that names no row, a cycle, or a superseded blocker. The copy holds no status of a row or of a wave, and the plan of a finished spec stores no wave: its section is one line. The copy does hold words that a format change can touch: the type word in `NN (checkpoint)`, the word "Phases", and, in the one line of a finished plan, the words open, resolved and superseded (F19, F24, F28, F106, F115, F129).
- Waves come from rows, not from phases. Two phases can share a wave, and one phase can lie in several waves (F22, F66).
- The shipped code works out live waves only. No code under `scripts/` on this branch, and none in the plugin 0.13.0, works out a fixed wave, a wave status, a phase status or a wait between two phases. DEC-030 and DEC-042 describe those for the views of IDEA-015. A throwaway prototype on the branch `prototype/views-board` of this repository works out all four (F31, F58, F59, F110).
- These instructions act on them. The planning skill writes the checkpoint rows, their blocks and the section. Both plan commands and the spec skill tell the agent to put checkpoints between phases. Both modes of `/build` write the section again at each row close. Only `/build auto`, with the incremental-implementation skill, starts every task on the frontier at once, up to the cap, moves the frontier after each closed row, and stops at a checkpoint row for the user's yes (F37 to F40, F42, F43, F45 to F50, F52, F134).
- A checkpoint holds back more in the build texts than its edges say. By the glossary, the planning skill and `brain check`, a checkpoint blocks only the later tasks that depend on its phase. By the build texts, a checkpoint row on the frontier stops every new start. No file stores that wider wait, and no test or eval tells the two readings apart. The reading by edges has two dated decisions by Peter. The stop has no row in the Decisions table and no line in the workspace spec (F104, F121, F133, C13).
- A wait on a checkpoint needs a task dependency today. `brain check` reports a task that names a checkpoint and depends on no task of that checkpoint's phase. The one worked example of waits between phases, the sample plan of the views prototype, gets six such findings from the shipped check (F27, F131).
- The scope of rows 09 and 10 is settled in part. IDEA-016 records as settled that "blocked by" works the same way for ideas, an idea's rows, specs, a spec's rows and phases; the how is open, in rows 09 and 10. DEC-050, which is accepted, names phases for the status values and for "one way for blocked by". The question that DEC-051 resolved named phases; the text of DEC-051 lists ideas, specs and their rows, and no phase (F112, F130).
- `brain status` has no word for a phase or a wave. It prints a checkpoint row as a step, with its Result when it is the last resolved row, and never lists it under "Waiting on the user". A spec is finished only when no row, checkpoint rows included, is `open` or `in-progress` (F30, F103, F105).
- No real plan in this repo has a checkpoint row, a phase in the glossary's sense or a wave from `brain plan`. The nine real plan files (eight under `specs/` and the one in `tasks/done/context-scope`) are all in the layout-1 form. Two of them have phases: there a phase is the tasks under a heading (SPEC-009) or under a plain line `Phase N: <name>` (SPEC-008). The SPEC-009 plan stores a wait between phases in a "Depends on" column and status words in its hand-made wave table, and those status words are stale today. Its todo stores each phase's state by hand. Each hand-kept copy of a phase's data differs from another source: the wait between phases from the task edges, the members in the plan from the members in the todo, and the order of the closes from the "Depends on" cell (F86 to F93, F109, F120, F137, F139).
- Two other repos on this machine hold a layout-2 plan. Neither plan has a checkpoint row. The finished one stores no wave: its section is the one line "No open rows" (F124).
- The question of row 09 has an earlier answer outside this worktree. Three draft decisions of 2026-11-05 first made a phase a real group with its own Blocked by, and then removed the words phase and checkpoint. They are held as unapproved drafts, and this worktree does not hold them (F125, F126).
- Twenty-two contradictions between sources are in "Contradictions between sources" below.

Where the definitions differ:

- **Direct or through other rows.** The glossary says "waits on". The code and the planning skill count only the task rows that the checkpoint names directly. In one fixture a checkpoint names row 02 only, row 02 waits on row 01, and row 01 is in no phase. The workspace spec says "its blockers"; the code counts only blockers of the type `task` (F10, F81, C17).
- **Checkpoint first or phase first.** By the glossary and the code, a phase exists only through its checkpoint. The plan commands say "Add checkpoints between phases", the spec skill says "Define verification checkpoints between phases", and the planning skill's check list says "between major phases". These lines treat a phase as a thing that exists before its checkpoint (F11).
- **One word, several senses.** "Checkpoint" is also the one approval of the plan in `/build auto` ("Single checkpoint"), a list of "Verification checkpoints" in the layout-1 plans, and "human checkpoints" in the orchestration reference. "Phase" is also a skill's own section (the glossary entry names idea-refine and debugging as examples; idea-refine has "three phases"), the parts "Phase A" to "Phase C" of the ship command and, in older text, the lifecycle; the spec skill now names its own four steps stages. The debugging skill has a "Cheap checkpoint" and a "Phase 1", and a vendored table of the constraint skill has a column "Phase" for the stages BUILD to SHIP. The deprecation skill has one more sense: "Phase 1" to "Phase 5" of a rollout and "additive phases", which are steps of a release and not sections of a skill (F01, F06, F12, F45, F83, F93, F113, F118, F142).
- **Words that the two entries use and the glossary lacks.** The entries Phase and Checkpoint use the words task and plan. The glossary has 19 entries, and none is Task, Plan or Spec (F142).
- **Checkpoint and phase as one thing.** Peter writes "checkpoints (phases)". The notes of IDEA-015 record that the glossary keeps the two apart: the checkpoint is the row, and the phase is the tasks that it waits on (F60a).
- **A stop before the next task, or a block on the dependents.** The todo template calls a checkpoint's box "a check that must pass before the next task starts", and the build texts stop every new start. The planning skill and `brain check` let a checkpoint block only the tasks that depend on its phase. The glossary entry holds both: "the work stops there" and "no other task" (F02, F14, F104, C13).
- **Wave and frontier.** Every source calls a wave "the frontier". The two rules differ: the frontier takes `open` rows only, and wave 1 also takes `in-progress` rows (F20, contradiction C1).

### 3. The code and its rules

Row 18 (RES-093) owns the depth of this code. These are the rules that this topic needs.

- **Rows.** A plan row has the type `task` or `checkpoint` and the status `open`, `in-progress`, `resolved` or `superseded by NN` (F13).
- **Waves.** `layWaves` takes the rows that are `open` or `in-progress`. Wave 1 holds each such row whose blockers are all `resolved`. Each later wave holds each row whose blockers are `resolved` or in a wave above. A `resolved` or `superseded` row is in no wave, so a row's wave number changes when an earlier row resolves (F19).
- **Critical path.** One row from each wave, each blocked by the one before; on a tie, the first row in table order (F21).
- **Phase.** For each checkpoint row that is not superseded: the rows of type `task` that its Blocked by cell names directly. A checkpoint in that cell is not in the phase (F22, F27).
- **Phases that share a wave.** `brain plan` lists each two phases that have a wave in common. This is the only use of a phase in `brain plan` (F22).
- **The checkpoint rule of `brain check`.** A checkpoint must block every later task that depends, through task rows alone, on a task in its phase, and no other task. The two tests differ in reach. "Blocks too much" looks only at a task that names the checkpoint in its own Blocked by cell. "Does not block" fires only when no path through rows of any type leads from the task to the checkpoint. So a block through another row passes, and a task that waits on a checkpoint only through another row is not tested for "too much". A task that the checkpoint itself waits on is exempt. A task that names a checkpoint and depends on no task of its phase is reported: the design source decided that "a task that names only the checkpoint is reported". So a task cannot wait on the review of a phase that it does not build on, and a wait between two phases with no task dependency has no form that passes `brain check`. One checkpoint can name another checkpoint (probe B); that orders the two reviews only (F27, F79, F102, F131).
- **The waves rule of `brain check`.** A plan with rows must hold a "Parallel waves" section equal to what `brain plan` prints above its Cap line. A plan with no rows needs none. A plan that `brain plan` cannot put in order gets the problem that `brain plan` names, and needs no section. A file with `migrated: 0.8` is not checked. A plan with one row that breaks the row format gets neither the checkpoint rule nor the waves rule (probe L). The section ends at the next heading of level 1 or 2, so a line of prose inside it makes it stale (probe K) (F28, F29, F106, F114).
- **When the stored section goes stale.** The printed text holds no status of a row. A row that goes from `open` to `in-progress` leaves the section current. A row that goes to `resolved` makes it stale, so the section is written again at each row close (probe J, F50, F115).
- **The stored section and a change of words.** `brain check` compares the stored text with the text that the code renders now. So a change of a word in the renderer makes each stored section stale until it is written again: the status words in the one line of a finished plan, the word "Phases", or `(checkpoint)`. The only instructions that write the section again are the planning skill and "Close a row". This record reads from them that no build step writes the section of a finished plan again, because that plan has no row left to close (F38, F50, F129).
- **Cap.** `BRAIN_MAX_PARALLEL`, then `max_parallel`, then 8. The cap has two readings. The code counts each wave alone: `brain plan` prints `min(tasks of the wave, cap)` as the tasks that start at once, and a checkpoint is not counted as a task. The build texts count across the build: "up to the cap counted with the tasks still running", and the workspace file says "the most sub-agents that run at once". A running task keeps its row `open`, so each new `brain plan --json` of a build puts the running tasks in wave 1 again and counts them under `startAtOnce` (probe P). No instruction names `startAtOnce` (F18, F25, F46, F82, F134).
- **A build does not run wave by wave.** It starts the tasks of wave 1 of each new `brain plan --json` call and moves the frontier after each closed row. So a row of wave 2 can start while rows of wave 1 run. The end summary asks for a count "in each wave", and no build text says which wave a task is in when it starts after the frontier moved (F47, F49, F134).
- **What `brain check` does not test.** It accepts a task in two phases, a task in no phase, a checkpoint with an empty phase, a plan with no checkpoint, and a checkpoint that is `resolved` while its phase's tasks are `open` (F32, F33, F35).
- **`brain status`.** It has no word for a phase or a wave. "Next step" is the first frontier row in table order, so a checkpoint row on the frontier is the next step only when it is first; in probe B a checkpoint is on the frontier and a task is the next step. "Last step" is the highest-numbered `resolved` row with its Result, a checkpoint row included. "Red" counts the checkpoint findings and the waves findings of `brain check`. `--json` gives each step its `type`, so a checkpoint row reads `checkpoint` there. "Waiting on the user" lists only the decide rows of a map, so it stays "none" for a checkpoint (F30, F103).
- **Which plan `brain plan` reads.** With a spec named, that spec's plan. With none, the plan of the active effort, which the git branch can name. It exits 2 and gives no wave when no effort is active, when several efforts are not finished, and when the active effort is an idea. The build command names no spec for `brain plan --json` (F26, F46, F101).
- **A plan that cannot be put in order.** `brain plan` exits 1 and gives no wave for four faults: a row that breaks the table format, a blocker that names no row, a cycle, and a row that a superseded row blocks. The frontier has no such test and still names rows, so `brain status` and the one-task `/build` still have a next row (probes H, I, M and N) (F24, F101, F106, F145).
- **A spec's finished state.** A spec is finished when no plan row is `open` or `in-progress`. The row type is not tested, so an open checkpoint row keeps its spec the active effort, and the close of a last checkpoint row finishes the spec. Each of the nine spec folders SPEC-001 to SPEC-009 counts as finished, whatever its phases say: eight hold a layout-1 plan with no row table, and SPEC-007 holds no plan. `tasks/done/context-scope` is not under `specs/`, so the code does not list it as an effort (F105).

What no instruction says:

- The one-task mode of `/build` names no checkpoint. Its steps describe a task (F51).
- No instruction of the plan or build stage sets a plan row to `in-progress` (F56).
- The protocol, the router, the status command and the hooks name no phase, checkpoint or wave (F55).
- No instruction says what to do with the output "Phases that share a wave". The planning skill lists it as a part of the section. The build command's only use of a phase is "present the checkpoint: what its phase built" (F48, F107).
- No instruction limits the stop at a checkpoint to the tasks that depend on its phase (F104).
- No instruction names the status that a checkpoint row gets. The checkpoint text says "close the checkpoint row", and "Close a row" names a task's commit, a task's block and a task's row. So `resolved` for a checkpoint row is an inference. RES-092 states the same (F116).
- No instruction says what the session does at a checkpoint when the user's reply is not a yes. For a failed check the build command holds only its general rules: stop and ask, and the debugging skill (F116).
- The protocol's "Task end" tells every session to update a row's status and result link and to keep user waits in rows and records. It names no checkpoint. A plan has no row type for a step that the user runs; the checkpoint row is the only row type that a build text ties to the user. A task row can also wait on the user in a build, for a sign-off or an answer, and no field stores that wait (F117, F134).
- No decision asks for the stop of a build at a checkpoint. The build texts hold it, and their guard test names a Decisions row as its source that does not hold it (F133).
