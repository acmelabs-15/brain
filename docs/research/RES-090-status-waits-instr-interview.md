# RES-090: How the interview skills handle status and waits

<!-- Add outcome: answered, partial or blocked to frontmatter when an answer or a block is known. Only answered work can become resolved. -->

## Question
How do the interview skills set, change and rely on status and waits: interview-me, idea-refine, prototype, domain-modeling, ask-user-question, wait-what, handoff and the researcher agent?

## Answer
Sufficient answer: with a source per claim, for each item kind, each instruction that sets or changes its status, with the file, the value, the lifecycle moment and the writer (main session, sub-agent, user, CLI). Each instruction that writes, changes or repairs a wait. Each instruction that relies on reading a status or a wait. The rules for a research record's status and outcome and for a decision record's status. How a wait on the user and a pending question are recorded. Every place where instruction text names a status value or a wait word as a literal. Where two of these skills handle the same concept differently. For each file, whether it is vendored or Brain-owned. What could not be established, and contrary evidence.

The evidence answers the question for the named decide rows. This record gives facts only. It gives no design and no recommendation. The Findings section holds one sourced claim per line, in groups A to J. The tables below point to those groups. The open points are under "Not established, and contrary evidence".

### Summary

- interview-me holds almost every rule, in three files. In this topic it is the only skill that changes a row's status or a Blocked by cell after the first write. An idea file has other writers: a standalone idea-refine run writes the first file, spec-driven-development (row 22) also sets `specced`, and the setup migration (row 20) writes an idea with no status (groups B, C, D).
- idea-refine writes a new idea file with `status: define` and rows that are all `open`. Inside an interview it writes one decision record and leaves the idea file to interview-me (groups B, C, E).
- domain-modeling owns the decision record's status. A research record's status and outcome come from three places: the research brief for a research row, interview-me's "Do rows" section for a do row, and the record template (groups E, F).
- ask-user-question owns the rules of the question exchange and of the wait for a reply. The workflow that called it owns the record of the wait. ask-user-question names no file and no field (group G).
- Three stored forms hold a wait on the user. The first is `status: proposed` on a decision record: the code checks it, and no instruction says when to write it. The second is `status: parked` on an idea: no instruction names the writer or the step. The third is a do row for a step that the user runs, with the Blocked by links of the rows that need it: the protocol names it (row 23), and no field says that the user is the one who acts. interview-me keeps a pending question as prose in the idea's Notes (groups B, E, G, H).
- Blocked by holds back only an `open` row. The frontier is the only reader of the cell. No check reports a blocked row that is already `in-progress` or `resolved`, and three rows of IDEA-016 are in that state (group D).
- prototype, handoff and wait-what name no status value, no map row and no Brain record ID. handoff names specs, plans and ADRs only as documents to point to. prototype and handoff are vendored (groups A, G, H).
- The researcher agent's body is one sentence. Its status rules come from the brief and from the record template (group F).
- A wait between two efforts has no place in the instruction text of these files. The only wait between items is the Blocked by cell, with row numbers of the same map. This repo's own ideas write a wait between two efforts as prose in Notes (groups D, I).
- Three independent checks ran on this record, in two rounds. The second round reported 41 issues. All 41 hold, and all are fixed. The results are under "Checks".

### 1. Status: who sets each value, and when

"Main session" means the session that the user talks to. interview-me sets it against a sub-agent and names it as the only writer of the idea during an interview (group C). The text does not define it by a skill. A standalone idea-refine run has no interview, so this record names its writer "the session that runs idea-refine". "The session that runs the skill" means the reader that the instruction addresses; the text gives that reader no other name.

### 4. A wait on the user and a pending question

Three stored forms hold a wait on the user:

- `status: proposed` on a decision record, "while the decision waits on the user" (skills/domain-modeling/DEC-FORMAT.md:40). The code accepts and checks the value. No instruction tells an agent when to write it, no real decision record holds it, and one eval grader rejects it (group E).
- `status: parked` on an idea. The workspace instructions say that a parked idea "waits until the user names it" (docs/agents/workspace.md:67). No instruction names the writer or the step. Three real parked ideas say in Notes that the idea waits on the user, and each still has open rows (groups B, I).
- A do row for a step that the user runs, with its exact command and the Blocked by links of the rows that need it (protocol/PROTOCOL.md:54). The row's type and status do not say that the user is the one who acts (group G).

interview-me does not use `proposed` for a pending question. It keeps the question as prose in the idea's Notes, tied to a row, and makes the decision record only after the answer. ask-user-question sets the rules of the wait and names no place to store it. The details are in groups E, G and H. In short:

- The main session records the pending question and its row before it asks. It clears the note when the answer is applied or the question is retired.
- This rule has a gap. For an ideate row, idea-refine asks the questions and may not write the idea file. For a prototype row, the prototype skill names no record. No instruction names who writes the pending-question note or a partial-answer note for these two row types.
- A partial answer keeps the decide row `open`. The settled part and the open part go into a Notes block.
- The agent adds no time limit: an unanswered question stays pending. Silence, a host expiry, an empty answer map and a delivery receipt are not answers. A host can set a limit of its own. Claude Code has a setting with 60 seconds, 5 minutes or 10 minutes, and its default is never. Codex gives a request outside Plan mode sixty seconds of grace and a sixty-second countdown.
- A delegation by the user ends the wait for its scope. The main session records the delegation and its scope; the text names no place for that record.
- When research returns while a question waits on the user, the main session keeps the pending question, saves the research record at once, and ends that exchange first. When the new evidence invalidates a premise of the question, it explains the correction in that exchange.
- A run with no way to ask records the missing answer and the rows it affects, reports that block, and continues only independent work.
- Work that only the user can do is a do row. The agent gives the user a checklist and keeps the next step in the row's research record.
- Work that delivers the destination waits on the user's confirmation of the intent. No field stores this wait; the `Confirmed by` line is its only mark.
- A sub-agent does not ask the user. The protocol says "A sub-agent returns user questions in its result file" (protocol/PROTOCOL.md:45), and a research sub-agent replies with its record path only. The host references support this in part: Claude Code keeps its question tool from Agent-tool sub-agents, and the Codex synchronous tool rejects non-root agents. The Gemini CLI reference names no sub-agent, and an SDK host can collect input in another way.
- `brain status` shows only a part of these waits (row 03 in section 8).
