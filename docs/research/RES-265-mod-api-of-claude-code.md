### What it gives for row 05 of IDEA-015

- **One tool.** A mod registers a tool with `$.tool.register`, and a hook of the mod is its handler (Part A, part 3). Tested: the main session, a foreground sub-agent, a background sub-agent and workflow agents each got it (Part B, tests 1 to 4).
- **One slash command.** A mod can register "a `/command` that runs your function at once, with no Claude turn" (Part A, part 4b). This is stated by the docs and not tested.
- **A session with no person.** Hooks run in `claude -p` (Part A, part 6). Tested: each test of Part B ran in `claude -p`, and the tool of the mod loaded there by `--plugin-dir`.
- **Who calls.** The handler gets the agent ID of a sub-agent or a workflow agent; on the main session it is absent (Part B, tests 1, 3, 4).
- **Start a turn.** `$.prompt.submit` waits until the session is idle and starts a turn (Part A, part 2). The old record RES-185 measured that; the main session did not read RES-185.
- **Start an agent.** `$.agent.spawn` runs an agent in the background (Part A, part 2). Stated, not tested here.
- **Reach the server.** The handler reaches a local server through `$.http.fetch`, also over a Unix socket, or through a command such as a CLI. One fetch ends at 30 s (Part B, test 11). A CLI call took 33 ms to 241 ms (Part B, test 7).
- **A server that outlives the session.** A command of the handler can start one, with `nohup` and all three streams redirected (Part B, test 12).
- **Not known.** If a teammate gets the tool; what holds in an interactive session; if an installed mod behaves as a mod loaded by `--plugin-dir`.

By default the tool waits behind ToolSearch, as an MCP server's tool does (api.md, 2.1.330 type file). Whether it loads upfront where tool search is off for MCP tools is UNVERIFIED (part 3). #### 1. Events and what a hook can return

Each hook gets `$`, the event `e` (frozen) and `next`. A hook observes (`return next(e)`), rewrites (`next({ ...e, x })`) or answers (returns a result and does not call `next`). A hook that fails before it calls `next` is skipped; when it fails after `next` resolved, that result stands. A guard needs a `.catch` handler to fail closed.

| Group | Events | What a hook can return | What the board can use |
|---|---|---|---|
| Tools | `tool.call`, `tool.check`, `tool.judge` (2.1.326), `tool.run` (2.1.326), `tool.describe`; in the 2.1.330 and public type files also `tool.offer` and the `tool.list` call | `next(e)`, `{ deny }`, `{ result, context? }`; `{ decision }` on `tool.check` | Each tool call of each loop, with `agentId` (absent on the main loop). `context` puts text after the tool's result for the model; none on a plugin's own `$.tool.call`. That it reaches a subagent's model is UNVERIFIED (open test 2). |
| Agents | `agent.offer`, `agent.spawn` (subagent, teammate, workflow agent, resumed run); 2.1.330 and public type files: `agent.report` | `{ isOffered: false }`; `next({ ...e, model })` or `{ deny }`; for `agent.report` `{ text }` or `{ consumed }` | Who starts, with `parentAgentId`, `isTeammate`, `workflow.runId` and `resume.agentId` |
| Turns | `turn.start`, `turn.step`, `turn.complete` | `next(e)`; `turn.step` can change the model; `turn.complete` can add a line under the answer | The start and end of each loop's turn, with `agentId` and `isAborted` |
| Session | `session.start`, `session.end`, `session.compact`, `session.receive`, `session.send`, `session.append`, `session.attach`, `session.detach`, `session.measure`, `session.stop` (2.1.326); public type file only: `session.state` | `{ skip }`, `{ consumed }`, `{ isDelivered: false }`, a changed row | Registration at start; messages between agents and sessions; `busy`, `waiting` or `idle` |
| Prompts | `prompt.submit` and eleven others | `next({ ...e, context })` adds text only Claude reads; `{ drop }` | A short board note on each prompt of the user |
| Settings hooks | `classic.<Event>` for each settings hook event | as `next(e)` and what the settings hook returns | Not usable where the built-in guard loads (see part 5) |
| Calls | Each `$` method is also an event, such as `fs.read` | `next(e)`, `{ deny }`, `{ value }` | Policy of other mods only |

Tested since (Part B, test 9): a `context` that the handler returns reached the model of the main session, of a foreground and a background sub-agent, and of workflow agents.

#### 2. Functions of the mods API and their limits

| Namespace | Methods | Limits and notes |
|---|---|---|
| `$.clock` | `now`, `sleep`, `after`, `every` | A timer runs outside any event, between turns, and starts no turn. Timers stop when the module reloads. |
| `$.prompt` | `submit`, `read`, `fill`, `suggest`, `compose` | `submit` waits until the session is idle and starts a turn. It is refused after the user stops a turn, until the next input. In `claude -p` its turns count toward `--max-turns`. |
| `$.agent` | `register`, `spawn`, `list`, `call` and `limits` (2.1.326) | `list` gives subagents and teammates with a status; the type files say it does not give a workflow's agents. `spawn` runs in the background. |
| `$.session` | `messages`, `cwd`, `root`, `model`, `turns`, `id`, `repo`, `surfaces`, `usage`, `version`, `info` (2.1.326), `compact`, `send`, `append`, `authorize` | `send` makes the delivery that SendMessage makes, to a session, a subagent or a teammate. `messages()` gives the newest 4,096 entries. |
| `$.tool` | `register`, `call`, `check`, `list` | See part 3. A mod's own `$.tool.call` raises no permission prompt (2.1.321). Whether deny rules cover it: the sources conflict (part 8). |
| `$.store` | `get`, `set`, `delete`, `keys` | 4 MiB of JSON in all, shared by every session on the machine; a get then a set is not atomic. |
| `$.state` | `get`, `set` and helpers | Lasts for the session and a reload; `/clear`, `/resume` and `/branch` reset it. |
| `$.fs` | `read`, `write`, `list`, `exists`, `stat`, `ancestors` | 4 MiB per file; from v2.1.326, `$.fs.read(path, { offset, length })` reads a larger file in parts. `write` is not atomic. No method watches a file. |
| `$.process` | `run`, `spawn`, `hookEnv` (2.1.326) | `run`: no shell, 30 s default, 10 min at most, 4 MiB per stream. `spawn`: streams output; the child lives until the loop ends, `next.signal` aborts or the module unloads. `hookEnv`: the session and plugin variables, among them `CLAUDE_CODE_SESSION_ID`; no agent ID. |
| `$.http` | `fetch` | http or https through the host; `socketPath` sends it over a Unix socket. Docs: 30 s per call, 4 MiB per body, 5 redirects. The 2.1.330 type file gives no `timeoutMs`; only the public type file gives `timeoutMs` up to 10 min. Refused for every mod where the organization's policy does not allow WebFetch. |
| `$.mcp` | `call`, `connect` | `connect`: the reference names a server that the mod's own manifest lists; the 2.1.330 and public type files add any server that /mcp lists (part 8) |
| Other | `$.plugin`, `$.ui`, `$.theme`, `$.command`, `$.model`, `$.turn`, `$.config`, `$.settings`, `$.env`, `$.wasm`, `$.audio`, `$.telemetry` | `$.ui.status`, `toast`, `log` and `notify` show text with no turn; `$.ui.log` is not read by Claude. |

A hook's own run time is 10 s, not counting time inside `next` or inside a `$` call other than `$.clock.sleep`. The hooks module has no Node.js API, no timer globals and no file or network access of its own. Installed mods share one worker thread; a hook that blocks it can get its mod unloaded.

#### 4. How a mod reaches a server process

A tool handler of a mod has no network or file access of its own; it reaches a local server only through `$` calls:

| Way from a handler | What the sources say | Time limit while the handler waits |
|---|---|---|
| HTTP over TCP | `$.http.fetch` to an `http` or `https` URL, through the host. Where the organization's policy does not allow WebFetch, Claude Code refuses every mod's `$.http.fetch`; no source says whether that covers a `socketPath` call. | Docs: 30 s per call, 4 MiB per body. The 2.1.330 type file gives no `timeoutMs`. Only the public type file gives `timeoutMs`, 30 s by default, 10 min at most. |
| HTTP over a Unix socket | `$.http.fetch(url, { socketPath })`; the URL still gives path, query and Host. Example: `POST http://bridge/reload` over `bridge.sock`. | As above |
| A short command | `$.process.run([...])`, such as the Brain CLI: no shell, whole output read | 30 s by default, 10 min at most; 4 MiB per stream |
| A spawned process | `$.process.spawn` streams the child's output piece by piece; the child blocks when 1,048,576 characters wait unread | No time limit found; the child dies when the loop ends, `next.signal` aborts or the module unloads |
| An MCP server | `$.mcp.call(server, tool, args)` on a connected server, with no permission prompt; `$.mcp.connect` connects a server that the mod's own manifest lists (the type files add: or any server /mcp lists) | No limit found in the mod sources. mcp.md gives MCP tool calls a per-server `timeout` or `MCP_TOOL_TIMEOUT`; whether it holds for `$.mcp.call` is UNVERIFIED. |

For each of these the hook's own 10 s does not count the wait. The 2.1.330 and public type files say a registered tool's own `tool.call` or `tool.run` hook has no limit at all on its `$` waits. The docs and the 2.1.306 copy do not say this. Each `$` call keeps its own limit: one `$.http.fetch` call ends at 30 s in the docs, and the 2.1.330 type file gives no `timeoutMs` to change that. When the user stops the turn, `next.signal` aborts, and a hook may run on for `lingerMs` (5 s).

A process that outlives one event or one session:

| Point | What the sources say | Status |
|---|---|---|
| Outlives one event | Yes: work that outlives one event runs on a timer from `session.start`; a `$.process.spawn` loop started there and not awaited lives "for the session's life". Worked example: the `filetree` mod. | STATED |
| Outlives a reload | No: the module unloading kills a spawned child, and timers stop. | STATED |
| Outlives the session | At `session.end` "only a process a command let go of outlives it" (2.1.330 and public type files). So, as a reading of this line (UNVERIFIED), a command that the mod runs must detach the server itself. No source says how, and no test ran it. A `$.process.run` waits for the whole output, so a detached child that keeps a pipe open holds the call until its timeout. | STATED in part; UNVERIFIED how |
| Listens for a connection | No `$` method listens. UNVERIFIED inference from the method list: the mod is always the client, and the server never calls the mod. | UNVERIFIED |
| File watch | No `$.fs` method watches; a mod polls or spawns a watcher. | STATED (method list) |

After the user stops a turn, the events of a monitor that a mod started are dropped until the next input, and refused calls are not repeated. A timer callback and a spawned child keep running between turns.

Tested since (Part B): one `$.http.fetch` ended at 30 s, also with `timeoutMs: 60000` over a Unix socket (test 11). A command of the handler started a child that outlived the session: `nohup` with all three streams redirected (test 12). The handler ran a CLI in 33 ms to 241 ms for one call (test 7).

#### 5. How a mod ships in a plugin

- Files: `.claude-plugin/plugin.json` (no new required field), `hooks/hooks.json` with `"modules": ["./register.js"]`, and the hooks module, an ES module of `.js` or `.ts`, with no build step. The mod needs `types/index.d.ts` when it uses `$.state` or adds a namespace. `types` in the manifest names another path for that file; from v2.1.299, `types` can be left out of the manifest.

- Ways to load: an installed marketplace plugin (cached by version; an edit needs a new version), `--plugin-dir` or `CLAUDE_CODE_PLUGIN_DIRS` (one session, reloads on save), a plugin folder under `~/.claude/skills/` or the project's `.claude/skills/` (loads at session start; the project folder needs trust), or a plugin synced from claude.ai.

Anthropic can also turn installed mods off remotely ("the rollout switch served off").

An installed plugin is cached by version, so an edit needs a new version. `pluginConfigs` keys a `--plugin-dir` mod by `<name>@inline`. A load error shows as a transcript line in an interactive session with `--plugin-dir` (on stderr in `claude -p`), and in the debug log for an installed mod. The remote rollout switch names installed plugins.
- The built-in guard loads where the machine has managed settings or `managed-mcp.json`, or the session runs on a Team or Enterprise `/login`. There it keeps a user's mod from hooking `classic.*`, `prompt.compose`, `prompt.section`, `prompt.context`, `prompt.attachment`, `skill.prompt`, `session.compact` and `settings.read`. A board mod that needs these events fails in such an organization unless an administrator installs it as the organization's mod.
- Mods exist since 2.1.287 ("Added Claude Mods"). The overview says mods are on by default from 2.1.287 in the terminal and 2.1.286 in the Desktop app; the admin page says 2.1.286.

#### 6. Kinds of session

- Hooks run in the terminal, the Desktop Code tab, the VS Code chat panel, `claude -p`, the Agent SDK, Remote Control (on the local machine) and cloud sessions that the plugin reaches. Not in Desktop WSL sessions or Desktop SSH sessions for a local-only mod. Nothing draws in `claude -p`.
- Trust: in an interactive session in a folder with no trust yet, no mod loads until the user accepts the trust prompt.
- A stopped turn: calls that start new work are refused until the next input; queued prompts and commands are dropped; `session.stop` (2.1.326) tells a mod.
- Resume and clear: `session.start` does not fire again after `/clear`, `/resume` or `/branch`; `session.end` fires with a reason; `$.state` resets; `classic.SessionStart` fires with `source`. Teammates are not brought back after a resume.
- Compaction: `session.compact` fires; a changed tool description or prompt section without `breakPromptCache` waits for a new conversation or a compaction.
- Reload: module variables and timers reset; `session.start` runs again; a call from the old copy can be refused. When the worker stops and Claude Code traces it to one mod, it unloads that mod. When the worker stops three times and Claude Code cannot trace the stops to one mod, it unloads all mods that are not built in, until `/reload-plugins`.

#### 6. Kinds of session
- Hooks run in a terminal `claude`, in the Code tab of the Desktop app, in the VS Code extension's chat panel, in `claude -p` and the Agent SDK (no drawing), in Remote Control on the user's machine, and in a cloud session for a plugin that reaches it. - When a session resumes, "interactively or with `claude -p`, the mods already in its mods folder can load without asking" (mods that Claude wrote in that session). Source: https://code.claude.com/docs/en/plugins/mods/create.md (line 64), checked 2026-11-24.
