## 4. Cross-Unit Consistency and Synthesis Notes (`inv-addy-1` through `inv-addy-7`)

1. **Three-Layer Architectural Synthesis (Skill vs. Persona vs. Command):**
   `docs/agents.md` provides the unified architectural taxonomy tying together the inventory of prior units:
   - *Skills* (`inv-addy-1`, `inv-addy-2`, `inv-addy-4`): Procedural workflows with concrete step criteria and outputs (e.g. `code-review-and-quality`, `spec-driven-development`).
   - *Personas* (`inv-addy-5`, `inv-addy-7`): Role viewpoints that adopt a specific stance and output schema (e.g. `code-reviewer`, `security-auditor`, `test-engineer`, `web-performance-auditor`).
   - *Commands* (`inv-addy-4`, `inv-addy-7`): User entry points that wrap a single persona or orchestrate a parallel fan-out (e.g. `/review`, `/test`, `/ship`).
   This three-layer distinction directly resolves core questions for Brain's Phase 3 concordance and Phase 5 lifecycle spec.

2. **Definitive Clarification of the `/ship` Composition Discrepancy:**
   In `inv-addy-5`, an unresolved tension was noted between `docs/comparison.md:54` (which asserted a 4-persona fan-out including `web-performance-auditor`) and the persona definitions. `docs/agents.md:44, 60-78` provides the definitive intent: `/ship` strictly fans out to 3 personas (`code-reviewer`, `security-auditor`, `test-engineer`). Performance audits are explicitly excluded from `/ship` because performance is specific to web apps; including it would create false noise for CLI tools, backend microservices, or shared libraries. Web performance is intentionally isolated into direct invocation or the dedicated `/webperf` command.

3. **Orchestration Discipline: The Prohibition of Meta-Orchestrators and Persona Recursion:**
   `docs/agents.md:79-98` directly forbids meta-orchestrators ("deciding which persona to call") and peer-to-peer persona delegation ("Personas do not call other personas"). This connects to Claude Code's platform boundary ("subagents cannot spawn other subagents") and prevents recursive routing degradation and multi-hop token inflation.

4. **Multi-Platform Manifest Strategy and Version Parity (D-009 Parity):**
   Brain's D-009 decision requires dual-target delivery for Claude Code and Antigravity. `sources/addy` demonstrates this in practice:
   - Root `plugin.json` serves Antigravity CLI (`agy`).
   - `.claude-plugin/plugin.json` serves Claude Code.
   - `.codex-plugin/plugin.json` serves Codex.
   `scripts/validate-versions.js` enforces that all 5 manifests remain locked to the same semantic version tag. Brain should adopt this pattern in Phase 7 to guarantee that `.claude-plugin/` and `.agents/` manifests stay in sync.

5. **Lifecycle Sequencing Variations:**
   `docs/agents.md:55` documents sequential slash commands as `/spec → /plan → /build → /test → /review`. This differs slightly from `README.md:41` (`spec → plan → build → test → review → ship`) and `skills/code-review-and-quality/SKILL.md` (which positions review after implementation but before or in parallel with final verification). This ordering is a primary candidate for Phase 3/4 alignment.
