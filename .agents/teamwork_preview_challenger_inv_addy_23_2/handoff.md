## Challenges

### [Low] Challenge 1: Concept Citation Tokenization in Compiled HTML Attributes
- **Assumption challenged**: That 100% of concept names in `## Concepts named` are exact literal substrings in the raw source file on disk at the exact cited line number.
- **Attack scenario**: The assigned sources in `sources/addy-external/` are compiled HTML documents generated by Astro. Automated string scanning against raw source text revealed:
  1. `external-incremental-implementation-md.md:117-119, 125-127, 132-133`: Concepts `#testing`, `#tdd`, `#quality`, `#context`, `#agents`, `#mcp`, `#documentation`, and `#correctness` cite line 12 with a `#` prefix. In the raw HTML file at line 12, they exist as space-delimited tokens in HTML attributes: `data-tags="testing tdd quality"`, `data-tags="context agents mcp"`, and `data-tags="documentation correctness"`. In contrast, line 5 has literal `#` prefixes inside rendered tag pills (`<span class="tag">#implementation</span>`).
  2. `external-planning-and-task-breakdown-md.md:109` and `external-incremental-implementation-md.md:137`: Concept `Teach & share` cites line 15, where the raw HTML source entity is `Teach &amp; share`.
  3. `external-incremental-implementation-md.md:84`: Concept `thin vertical slices` cites line 12, where the actual text on line 12 is `thin, tested vertical slices` (with the word `tested` inserted), whereas the exact unpunctuated phrase `thin vertical slices` appears verbatim on lines 1 and 5.
  4. `external-planning-and-task-breakdown-md.md:118` and `external-incremental-implementation-md.md:146`: Concept `Addy Osmani` cites line 1 and line 16. Line 1 contains the Twitter creator handle `@addyosmani`, whereas the exact string `Addy Osmani` appears at line 16.
- **Blast radius**: Zero for Phase 1. These minor discrepancies stem from extracting human-readable text from compiled HTML/DOM attributes rather than markdown source. They do not impair semantic modeling in Phase 2.
- **Mitigation**: In Phase 2 concept modeling, miners should cite line 5 or the raw attribute without `#` prefixes and note HTML entity decoding.

### [Low] Challenge 2: Spanning Multi-Line Purpose Citation Normalization
- **Assumption challenged**: That multi-line purpose citations in compiled HTML can be matched as single contiguous string literals without whitespace collapsing.
- **Attack scenario**: The package tagline in both entries cites lines 13–14:
  `> "Production-grade engineering skills for AI coding agents. Encode senior-engineer workflows across the full lifecycle." — ../addy-external/planning-and-task-breakdown.md:13-14`
  Line 13 ends with `senior-engineer\n` followed on line 14 by ten spaces of indentation before `workflows across the full lifecycle.`. Direct `.includes()` substring search on raw text fails without whitespace normalization.
- **Blast radius**: None. Normalizing whitespace collapses the newline and indentation into a single space, yielding a 100% exact match.
- **Mitigation**: Document whitespace normalization for multi-line HTML text blocks.

### [Low] Challenge 3: Perfect Self-Reported Byte Size in Work Unit Report
- **Assumption challenged**: That the work unit report might exhibit self-referential byte drift if the report's size was recorded prior to final write.
- **Attack scenario**: In earlier units (e.g. `inv-addy-20`), the unit report's self-reported byte size differed slightly from the final file size on disk (+715 bytes).
- **Result**: In `inv-addy-23`, the reported size in `inv-addy-23.md:18` (`4,554 bytes`) matches the on-disk file size (`4,554 bytes`) down to the exact byte. Both inventory entry files also match their self-reported sizes (17,569 and 21,169 bytes) with zero drift.
